模块化单体架构#

状态：有效 | 最后核对：2026-11-10 | 对应代码：web-api/src（六项目结构与 QPS.Host/Registration、QPS.Shared/Pipeline）

后端为 .NET 8 模块化单体：一个进程、一个数据库，按业务模块拆分项目，模块通过 AddQpsXxx() 显式启用。

1. 项目与职责#

项目职责关键内容
QPS.Shared与业务无关的公共契约和横切能力BaseEntity、ApiResponse、分页、JWT 配置、IUnitOfWork、IPermissionChecker、ICurrentUserService、PermissionAttribute、领域事件契约、三个 Pipeline Behaviour
QPS.System系统能力用户、角色、权限、数据字典、行政区、操作日志、错误日志；登录、权限检查器
QPS.CrmCRM 业务药材基地主体/基地/供应、联系人、跟进、流转、厂商、采购需求、撮合机会、业务活动
QPS.Mall商城业务商品/SKU/分类/标签/评价、购物车、订单/支付/退款/退货/发货、促销/优惠券/活动、会员/地址/积分、内容页
QPS.Persistence持久化基础设施单一 AppDbContext、三套模型配置、迁移、种子数据、CurrentUserService、JwtGenerator
QPS.Host组合根与 HTTP 基础设施Program.cs、上传控制器、响应包装过滤器、异常中间件、MVC/JWT/CORS/Swagger 注册

2. 依赖方向#

QPS.Host ──> Shared, System, Crm, Mall, Persistence
QPS.Persistence ──> Shared, System, Crm, Mall
QPS.Crm ──> Shared, System
QPS.Mall ──> Shared
QPS.System ──> Shared
QPS.Shared ──> 无业务模块依赖

约束由 web-api/tests/QPS.ArchitectureTests/ProjectReferenceTests.cs 和 ModuleBoundaryTests.cs 固化：

  • QPS.Shared 不引用任何业务模块或 Host。
  • QPS.System 不引用 Crm、Mall、Persistence、Host。
  • QPS.Crm 不引用 Mall、Persistence、Host。
  • QPS.Mall 不引用其他业务模块、Persistence、Host。
  • QPS.Persistence 不引用 Host。
  • Mall 的 Feature 不得直接引用其他 Feature 的 Handler。

3. 模块内分层#

业务模块（System / Crm / Mall）保持四层目录：

QPS.Xxx/
  Domain/          实体、值对象、领域服务、领域事件
  Application/     Features/<业务>/*Command|*Query|*Handler|*Validator
  Contracts/       模块对外的 DbContext 接口与 DTO
  Controllers/     HTTP 入口，只调用 IMediator
  • Domain：只依赖 QPS.Shared，不依赖 MediatR、EF Core 或 ASP.NET Core。
  • Application：按 Feature 垂直切分，一个用例一个 Handler；查询命名 XxxQuery，命令命名 XxxCommand。
  • Contracts：暴露 ISystemDbContext / ICrmDbContext / IMallDbContext 及 DTO，供 Persistence 实现、供 Controller 使用。
  • Controllers：不写业务逻辑，只把请求转成 Command/Query 并 Send。

QPS.Shared 分层：

Common/      BaseEntity、ApiResponse、PaginationRequest/Response、JwtOptions
Contracts/   IUnitOfWork、ICurrentUserService、IPermissionChecker、PermissionAttribute、
             IAllowAnonymousRequest、IDomainEvent、IDomainEventDispatcher、IJwtGenerator
Pipeline/    PermissionBehaviour、ValidationBehaviour、TransactionBehaviour、领域事件派发
Exceptions/  BusinessException（由 Host 异常中间件统一转换为响应）
Extensions/  通用扩展（CurrentUserExtensions、PaginationExtensions）

QPS.Persistence 分层：

Database/        AppDbContext（同时实现 ISystemDbContext、ICrmDbContext、IMallDbContext、IUnitOfWork）
Configurations/  SystemModelConfiguration、CrmModelConfiguration、MallModelConfiguration
Identity/        CurrentUserService、JwtGenerator
Migrations/      EF Core 迁移
Seeds/           MallMockDataSeeder（仅 Development）

QPS.Host 分层：

Controllers/   FileUploadController、MemberFileUploadController
Filters/       ResponseWrapperFilter
Middleware/    ExceptionHandlerMiddleware
Registration/  ServiceRegistrationExtensions（MVC、CORS、Swagger、JWT）
Properties/    launchSettings.json（5000/5001）

4. 模块启用机制#

Program.cs 中的注册顺序：

  1. AddQpsMvc() + ConfigureQpsApplicationParts(typeof(Program).Assembly)
  2. AddQpsCors()、AddQpsSwagger()
  3. 读取并绑定 JwtOptions，AddQpsJwtAuthentication()
  4. AddQpsShared()
  5. AddQpsPersistence(configuration)
  6. AddQpsSystem(mvcBuilder)、AddQpsCrm(mvcBuilder)、AddQpsMall(mvcBuilder)

每个 AddQpsXxx() 做两件事：

  • 用 AddMediatR(cfg => cfg.RegisterServicesFromAssembly(...)) 注册本模块 Handler。
  • 把本模块程序集加入 MVC 的 ApplicationParts，暴露本模块 Controller。

ConfigureQpsApplicationParts 会先清空默认发现范围，再加入 Host 自身。因此未调用 AddQpsXxx() 的模块既不注册 Handler，也不暴露 Controller，ModuleRegistrationTests 对此有覆盖。

Mall 额外注册了促销策略与购物车处理器：

  • DiscountAmountAction、DiscountRateAction、GiftAction、FreightFreeAction
  • IActionStrategyRegistry、MallPromotionEngine、MallPromotionContextBuilder、MallPromotionPreviewService
  • MallCouponService、MallProductPromotionEnricher、GetMallCartHandler

5. Pipeline Behaviour 的真实约束#

三个 Behaviour 在 QPS.Shared/DependencyInjection.cs 中的注册顺序就是执行顺序，Permission 在最外层：

PermissionBehaviour  →  ValidationBehaviour  →  TransactionBehaviour  →  Handler

5.1 PermissionBehaviour#

  • 请求实现 IAllowAnonymousRequest，或 Endpoint 标记 [AllowAnonymous]：直接放行。
  • 已登录 member 角色且 Endpoint 使用 MallMember 策略：放行（移动端会员接口）。
  • 否则要求 ICurrentUserService.UserId 是有效 Guid，且用户 IsActive，否则抛出 401 BusinessException。
  • 从请求类型的 [Permission("...")] 读取权限码，缓存于 PermissionMetadataCache；无权限抛 403。
  • 权限判定链路：SystemUser.RoleId → SystemRolePermissions → SystemPermissions.Code。

约束：新增需要权限的接口时，把 [Permission] 标在 Command/Query 上，不要写在 Controller；Controller 只负责路由与 [Authorize] 策略。

5.2 ValidationBehaviour#

  • 收集当前请求类型的所有 IValidator<TRequest>，执行 FluentValidation。
  • 有错误时抛出 ValidationException，由 Host 的异常中间件统一转为业务错误响应。

约束：输入校验放 Validator，不在 Handler 里堆手写 if 判断；跨实体业务规则放 Domain。

5.3 TransactionBehaviour#

  • 请求类型名以 Query 结尾：直接 next()，查询不开启写事务。
  • 其余请求（Command）：BeginTransactionAsync → Handler → CommitAsync；异常时 RollbackAsync 后重抛。
  • AppDbContext.BeginTransactionAsync 内部有 Database.CurrentTransaction == null 判断，允许安全嵌套。

约束：

  • Handler 不得手写 BeginTransactionAsync / CommitAsync / RollbackAsync；需要事务的写操作必须命名为 XxxCommand。
  • Handler 可以按需调用 SaveChangesAsync；多步写入依赖外层事务保证原子性。
  • 只读逻辑命名为 XxxQuery，避免无意义的事务开销。

PipelineTests 强制约束：业务模块不得自己实现 IPipelineBehavior，三个通用 Behaviour 只能放在 QPS.Shared。

6. 持久化模型#

  • 全库只有 AppDbContext，同时实现三套模块契约与 IUnitOfWork。
  • OnModelCreating 依次应用 SystemModelConfiguration、CrmModelConfiguration、MallModelConfiguration，再挂软删除查询过滤器。
  • SaveChanges / SaveChangesAsync 统一处理：软删除、审计字段（CreatedAt/By、UpdatedAt/By）、操作日志。
  • BaseEntity 提供 Id、审计字段与 IsDeleted；业务代码不做物理删除，统一置 IsDeleted。
  • 除 SystemOperationLog、SystemErrorLog 外，删除均转为软删除。

7. HTTP 基础设施#

Program.cs 请求管道：

Swagger → CORS(AllowAll) → StaticFiles(wwwroot, /uploads 长缓存)
        → ExceptionHandlerMiddleware → Authentication → Authorization → MapControllers
  • ResponseWrapperFilter 把所有 Controller 返回值包装为 ApiResponse。
  • DataAnnotations 校验失败返回 HTTP 200 + { code: 400, msg }，与异常中间件格式一致。
  • JSON 使用 camelCase，中文不转义。
  • JWT 默认 FallbackPolicy 要求已认证；预置策略 AdminOnly（admin）、MallMember（member）、AnyUser。
  • 上传目录 wwwroot/uploads 启动时自动创建；/uploads 响应带一年 immutable 缓存头。

8. 新增模块/功能的检查清单#

  1. 新模块项目只引用 QPS.Shared（确需系统能力才引用 QPS.System），不得引用 Host/Persistence。
  2. 在 QPS.Host/Program.cs 调用 AddQpsXxx(mvcBuilder)，否则模块不会生效。
  3. 在 QPS.Persistence 增加 IXxxDbContext 实现与模型配置，并让 AppDbContext 实现该契约。
  4. 写操作命名 XxxCommand 并依赖全局事务；读操作命名 XxxQuery。
  5. 需要权限的请求加 [Permission]；公开接口实现 IAllowAnonymousRequest。
  6. 新增跨模块能力时通过 Contracts 接口，不直接引用其他模块内部实现。

9. 协作与共享层约定（三端通用）#

  • 所有回答使用中文。
  • 修改范围保持最小，只改完成当前任务所必需的源码或配置；不得回退其他未提交改动。
  • 已有封装组件优先使用：各端项目中已有的封装组件（业务组件、布局组件、图表组件等），开发新功能时必须优先使用，不得绕过已有封装自行编写功能重复的代码。
  • 禁止直接修改基础组件与公共模块：各端的 components、layout、utils、api 拦截器、路由守卫、权限模块等共享基础设施，严禁未经确认直接修改。如需扩展或修复，必须先向负责人说明原因、影响范围和拟议方案，得到明确确认后才能执行。未经确认的改动一律退回。
  • 未获确认的改动仅限在业务页面/模块内部完成，不得扩散到共享层。

权限设计方案#

状态：有效 | 最后核对：2026-11-10 | 对应代码：web-api/src/QPS.System/Application/Services/PermissionChecker.cs、QPS.System/Application/Features/Permissions、web-api/src/QPS.Shared/Contracts/PermissionAttribute.cs、web-api/src/QPS.Shared/Pipeline/PermissionBehaviour.cs、admin/src/components/Permission、admin/src/assets/json/authMenuList.json

本文档用于让后续开发者或 AI 快速理解 QPS 项目的权限设计。当前方案追求简单、直观、少封装。

1. 核心原则#

权限码是唯一判断依据。

后端 SystemPermissions.Code 是权限来源，前端不再维护按钮权限映射表，也不再使用 BUTTONS.xxx 这类别名。

页面上需要控制权限的地方，直接写真实权限码：

<Permission code="CRM_HERB_BASE_CONTACT_PRIMARY">
  <el-button>设为主</el-button>
</Permission>

这样读页面时可以直接看到按钮受哪个权限控制。

2. 校验链路#

PermissionAttribute 标在 Command / Query 类型上，由 PermissionBehaviour 在 MediatR 管道里统一校验，Controller 与路由中间件不参与权限码映射。PermissionBehaviour.Handle 的实际顺序：

  1. 请求类型实现 IAllowAnonymousRequest，或端点元数据带 IAllowAnonymous → 直接放行。
  2. 已认证且角色为 member、端点上声明了 MallMember 策略 → 直接放行（移动端商城接口走这条）。
  3. ICurrentUserService.UserId 不是有效 GUID → 抛 BusinessException(401, "登录状态无效")。
  4. PermissionChecker.IsUserActiveAsync 返回不可用 → 抛 BusinessException(401, "当前用户不可用")。
  5. 请求类型上取到权限码且 PermissionChecker.HasPermissionAsync 不通过 → 抛 BusinessException(403, "无权访问该功能")。
  6. 以上都通过才进入 Handler。

权限码从类型上读取后缓存在 PermissionMetadataCache（按 Type 缓存 GetCustomAttribute<PermissionAttribute>()?.PermissionCode），因此同一个请求类型只在首次解析反射，不要在运行期修改特性。

登录态与角色策略在 QPS.Host/Registration/ServiceRegistrationExtensions.cs 里配置：默认策略要求已认证用户，另有 AdminOnly（RequireRole("admin")）、MallMember（RequireRole("member")）、AnyUser（仅要求已认证）三条策略。管理端 Controller 统一使用 AdminOnly，功能权限在此基础上由 PermissionBehaviour 二次校验。

2.2 双 provider 并行的可行性#

可以并行，但不能让两套迁移共存在同一个程序集：EF 的 ModelSnapshot 与迁移历史只认一个 provider，混放会导致 snapshot 互相覆盖。两种可行结构：

  1. 生产 SQL Server 保留迁移；SQLite 仅用 EnsureCreated（推荐，成本最低）
    • SQL Server：MigrateAsync() + 现有 49 个迁移。
    • SQLite：Database.EnsureCreatedAsync()，不生成迁移；开发/测试库可从空库直接建表。
    • 代价：SQLite 无法享受增量迁移，每次模型变化要删库重建；仅适合开发/测试。
  2. 按 provider 拆迁移程序集
    • 新建 QPS.Persistence.Sqlite（或把迁移拆到 Migrations/SqlServer 与 Migrations/Sqlite 两个程序集），通过 MigrationsAssembly 指定。
    • 代价：项目结构变复杂；两套迁移要同步维护；EF CLI 需要额外参数。

当前没有 IDesignTimeDbContextFactory，dotnet ef 依赖 Host 启动来获得 DbContext。改成配置驱动后，CLI 也必须带上 provider 配置，否则生成迁移时会拿到错误的 provider。

3. 金额与 decimal（本次最关键的阻断点之一）#

3.1 EF + SQLite 实际怎么存#

SQLite 没有 decimal 类型。EF Core 的 SQLite provider 默认把 decimal 映射为 TEXT，写入时按 invariant 字符串保存（如 "1234.56"）。迁移里的 decimal(18,2) 声明不会被 SQLite 执行，重新生成迁移后也不会保留精度语义。

后果分两类：

  • C# 侧读写是精确的：decimal → TEXT → decimal 往返不丢精度，领域层 MallOrder.CalculatePayableAmount、退款金额校验这些 C# 计算不受影响。
  • SQL 侧比较 / 排序 / 聚合是错的：
    • ORDER BY 按文本字典序："9.9" > "10.0"，金额排序会乱。
    • WHERE amount <= x 按文本比较，筛选结果错误。
    • SUM() 会把 TEXT 隐式转 REAL，产生浮点误差；MAX() 按文本比较。
    • TEXT 列上的索引对数值范围查询无效。

大小写敏感比较登录 LoginCommand.cs:92 用 u.Username == username；大量编码唯一索引行为变化SQL Server 默认 CI：Admin 能登录 admin；SQLite = 区分大小写，登录会失败。唯一索引在 SQLite 下也变成区分大小写，ABC 与 abc 可同时存在。需对用户名/权限码/商品码/券码等加 COLLATE NOCASE 或统一小写归一化
DateTime / DateTimeOffsetDateTime 大量；DateTimeOffset 为 0可用DateTime 映射 TEXT（固定宽度 ISO），排序与范围比较正常；DateTimeOffset 未使用，不构成风险
并发令牌无 rowversion / IsConcurrencyToken（0 处）无差异本来就没有乐观并发保护；SQLite 下同样没有。不要误以为单写锁等于并发安全，它只保证串行化
批量插入无 SqlBulkCopy；AddRange + SaveChanges可用但更慢SQLite provider 的批处理能力弱于 SQL Server，大量 AddRange（种子、订单明细）会产生更多往返；需实测种子耗时
裸 SQL（迁移/种子）52 处迁移 raw SQL不可用GETDATE()→CURRENT_TIMESTAMP、NEWID()→参数化 GUID、TOP (1)→LIMIT 1、IF EXISTS→WHERE NOT EXISTS；迁移需重新生成

6. 并发与事务#

6.1 现状#

  • 所有 Command 经 TransactionBehaviour 自动 BeginTransaction / Commit / Rollback（TransactionBehaviour.cs:24-33）。
  • 关键写路径：
    • 下单：CreateMallOrderCommand 在一个事务里做库存条件扣减（2 次 ExecuteUpdateAsync）、写订单/明细/流水。
    • 领券：MallCouponService 两次 ExecuteUpdateAsync（领券计数 + 会员券）。
    • 支付/退款/超时关单：MallOrderResolver 条件更新 + 库存回补，均在同一事务内。

6.2 SQLite 行为#

  • 单写锁：同一时刻只允许一个写事务；WAL 模式下读可以并发，写仍串行。
  • 事务从首次写入一直持锁到提交；上面的下单/退款事务包含多次写，锁持有时间会被放大。
  • Microsoft.Data.Sqlite 默认有 busy timeout（约 30 秒），但高并发下仍会出现 database is locked；开启 WAL 只能缓解读，不解决写排队。
  • 没有重试策略：TransactionBehaviour 没有 ExecutionStrategy 重试，SQLite 锁冲突会直接冒到接口。

6.3 判断#

场景判断
单实例、开发/测试、并发写 < 5/s、数据量 < 几十万行可接受（建议 journal_mode=WAL、busy_timeout=5000、缩短事务）
生产多用户下单、秒杀、支付回调峰值、多实例部署不可接受：写入串行化会直接成为瓶颈，且 database is locked 无法通过扩容解决
支付回调幂等单写锁反而降低并发竞争，但没有乐观并发/唯一幂等键时，仍可能重复更新；与 provider 无关

7. 软删除、审计、操作日志#

  • 全局查询过滤器 HasQueryFilter(e => !e.IsDeleted) 在 AppDbContext.OnModelCreating 中统一注册，属于 EF 模型层，SQLite 下行为一致。
  • 软删除、审计字段填充依赖 SaveChanges 拦截器/领域事件，均在 C# 侧执行，与 provider 无关。
  • 操作日志：系统在 SaveChanges 时为变更实体批量写日志。SQLite 下这些写入与业务写入在同一事务里，日志量越大事务越长，锁持有越久；表本身无上限增长，SQLite 文件会持续变大且难以在线收缩。
  • 差异点只有一个：过滤唯一索引依赖 HasFilter，SQLite 下需去掉 N'…' 并确认方括号写法；其余无行为差异。

  • 保存集合 = 勾选的页面 Menu + 勾选的 Button + 自动补齐的祖先 Menu + 保留的 ROOT。勾选任一按钮会自动带上其页面与模块，保证菜单路由可见。

3. 两栏职责与联动路径#

  1. 矩阵区：顶部模块筛选 chips + 行搜索 + 「全部展开 / 全部收起」+「全选访问」；主体为矩阵表格：
    • 分组行：模块名 + code，右侧三态全选框（全选/半选/未选，作用于该组所有页面行的访问开关）。
    • 页面行：页面名 + code（mono 小字），「页面访问权限」列是开关，右侧为该页面的按钮 chips。
  2. 右栏｜修改记录：相对已保存集合的实时 diff，卡片标注「新增授权 / 取消授权」+ 路径 + code；顶部显示待保存数量与「撤销所有」；保存后清空。

联动路径：

  • 角色切换入口只保留顶部角色下拉（不设左栏角色列表，也无下拉与列表的双向同步）→ 选择后载入该角色勾选态到矩阵与右栏 diff 基准。
  • 切换角色：载入新角色权限，未保存变更直接丢弃（与现有行为一致）。
  • 勾选页面开关 → 关闭时自动取消并锁定该页按钮（按钮 chips 进入只读态），同时刷新右栏 diff；打开时不自动勾选按钮。
  • 勾选按钮 → 自动同时勾选其页面与祖先模块（只影响展示与保存集合，不产生额外 diff 卡片以外的节点）。
  • 模块 chip / 搜索 → 只过滤当前展示的行，不影响已勾选集合与 diff 计算。
  • 重置 / 撤销所有 → 恢复到该角色已保存集合；保存 → PUT 成功后以当前集合为新基准。

4. 矩阵控件形态#

  • 全选（分组行）：el-checkbox 三态。组内页面全选 = 选中；部分 = indeterminate 半选；点击半选/未选 = 全选该组页面的「页面访问」；点击已选 = 全部取消（并联动清空按钮）。
  • 页面访问开关：el-switch，开=「允许访问」（主色 #009688），关=「已禁用」（灰色）；页面关闭时整行按钮区降透明度并锁定。
  • 按钮单元格：el-checkbox 内联流式排列，文案使用权限名称；code 以 tooltip 展示。删除类（code 结尾 _DELETE）加「高危」红色小标签，但仍可授权（现有系统没有后端锁定策略，不做假只读）。
  • 只读态：仅两种：ROOT 不可见/不可编辑；页面关闭后其按钮 chips 与组内联动处于 disabled。不引入角色级只读。
  • 空态：过滤后无命中显示「没有匹配的权限」；角色无权限时矩阵照常可操作。

2. 设计原则与边界#

2.1 设计原则#

  1. 画像与测评分离：画像只保存相对稳定的健康属性；体质结论只存在于测评记录，画像表不冗余 CurrentConstitution，避免历史结论被覆盖。
  2. 测评只增不改：已提交测评不允许修改答案、分数、主体质；需要修正时新增一条测评并注明来源，历史全部保留。
  3. 问卷版本不可变：已发布问卷的题目、选项、分值、反向标记不可编辑；修改必须新建草稿版本，发布后旧版本自动归档。
  4. 服务端计分：客户端只提交 questionId + optionId，不提交分值；分值、反向计分、判定全部在服务端完成，防止篡改。
  5. 最小必要：不采集身份证号、基因、人脸、金融等无关信息；健康文本只采集调养所需内容。
  6. 可审计：会员健康数据的字段级变更写专用变更日志；管理端读取写访问审计日志；通用 SystemOperationLogs 不承载健康明文。

2.2 v1 明确边界#

v1 做：

  • 健康画像的查询与保存；
  • 单独同意与撤回；
  • 问卷配置、发布、归档；
  • 体质测评草稿、提交、历史、结果；
  • 药师/客服查看会员健康档案、录入测评、追加建议；
  • 变更日志与访问审计。

v1 不做：

  • 商品“适宜体质/慎用体质”标签与筛选；
  • 基于体质的个性化推荐、排序、营销触达；
  • 孕哺期/过敏史的个性化商品匹配（仅在商品详情和结算页预留提示位置，展示通用提示）；
  • 问卷题目在代码中硬编码；
  • 测评结果导出、PDF、报告分享；
  • 多量表（除中医体质外的其他量表）；
  • 数据脱敏导出、字段级加密、自动保留期清理；
  • AI 生成建议、自动诊断、处方或用药推荐。

3.6 问卷版本与不可变规则#

  1. 新建问卷必须是草稿状态，可反复保存题目树。
  2. 发布前校验：
    • 至少一个题目；
    • 量表为 TCM_CONSTITUTION 时，九个体质维度都必须至少有一题；
    • 每题至少 2 个选项，分值互不重复且在 1–5；
    • 题号在问卷内唯一，选项编码在题目内唯一；
    • 所有 TCM_CONSTITUTION 题目 IsRequired = true。
  3. 发布时在同一事务内：
    • 将同 ScaleCode 当前已发布版本改为 Archived，写 ArchivedAt；
    • 当前版本改为 Published，写 PublishedAt。
  4. 已发布/已归档问卷的题目、选项、分值、反向标记禁止编辑。
  5. 已有测评引用的问卷不能物理删除；草稿可以软删除，已发布/已归档只能归档。
  6. 新版本发布后，旧草稿不自动迁移；用户需要重新作答新版本。

3.7 测评草稿与提交规则#

  • 草稿绑定 QuestionnaireId，并使用该问卷的 Version 快照。
  • 同一会员、同一问卷版本最多保留一个进行中的草稿；再次创建草稿时返回已有草稿。
  • 草稿允许部分作答、反复保存。
  • 提交时必须：
    • 草稿属于当前会员；
    • 草稿状态为 Draft；
    • 问卷状态不是 Draft（可以是 Published 或 Archived）；
    • 所有必答题已作答；
    • 每个答案的选项属于对应题目；
    • 会员存在有效同意记录（药师录入同样要求会员已同意）。
  • 提交后写入 SubmittedAt、Status = Submitted、主体质、兼夹、倾向、分数、原始答案。
  • 提交后不提供修改/删除接口；重复提交幂等返回已有结果。
  • 新版本发布后，旧版本草稿仍可提交，但响应标记 questionnaireOutdated = true，前端提示“已有新版本，可重新测评”。

3.8 审计与通用操作日志的关系#

现有 AppDbContext.cs 的 AddOperationLogs() 会对所有 BaseEntity 的增删改写 SystemOperationLogs，并把字段改前/改后完整写入 ChangeJson。这会把健康明文复制到通用操作日志，存在两个问题：

  1. 通用操作日志的查看权限与健康档案权限不一致，可能扩大健康数据可见范围；
  2. 同一份答案/病史会被重复保存，增加泄露面和存储成本。

建议在实施时做一个需要确认的共享层小改动：

  • 在 AppDbContext.AddOperationLogs() 中排除会员健康数据实体（MallHealthProfile、MallHealthAssessment、MallHealthConsent、MallHealthAdvice、MallHealthChangeLog、MallHealthAccessLog）；
  • 这些实体由 MallHealthChangeLogs / MallHealthAccessLogs 专用审计表覆盖；
  • 问卷配置实体（MallHealthQuestionnaire、MallHealthQuestion、MallHealthQuestionOption）不属于会员敏感数据，可继续走通用操作日志。

该改动触及 AppDbContext 公共基础设施，按工作区规则必须先向负责人确认后再实施。

4. 评分算法#

4.1 输入与输出#

输入：

  • 问卷版本 questionnaire（含题目、维度、反向标记、选项分值）；
  • 答案集合 answers：questionId -> optionId；
  • 会员、来源、测评时间由 Handler 提供。

输出：

  • 九项 raw、converted、measured；
  • 主体质 mainConstitution（0 表示未判定）；
  • 兼夹体质集合 secondaryConstitutions；
  • 倾向体质集合 tendencyConstitutions；
  • 每题的有效分与原始分，写入 AnswersJson。

4.2 计分伪代码#

FUNCTION ScoreAssessment(questionnaire, answers):
    ASSERT questionnaire.Status != Draft
    questions = questionnaire.Questions where IsDeleted = false

    // 1. 必答校验
    requiredQuestions = questions where IsRequired = true
    missing = requiredQuestions where answers does not contain question.Id
    IF missing is not empty:
        ERROR 400 "还有 {missing.Count} 题未作答"
              WITH missingQuestionCodes = missing.Select(Code)

    // 2. 答案合法性校验：题目存在、选项属于该题、题目必答
    FOR EACH (questionId, optionId) IN answers:
        question = questions.Find(questionId)
        IF question is null:
            ERROR 400 "答案包含未知题目"
        option = question.Options.Find(optionId)
        IF option is null:
            ERROR 400 "选项不属于对应题目"

    // 3. 逐维度计算
    resultScores = {}
    FOR type IN 1..9:
        items = questions where ConstitutionType = type
        n = items.Count

        IF n = 0:
            resultScores[type] = {
                raw: 0,
                converted: null,
                measured: false,
                judgement: "UNMEASURED"
            }
            CONTINUE

        rawSum = 0
        FOR EACH question IN items:
            option = answers[question.Id].Option
            score = option.Score                 // 1..5
            IF question.IsReverseScored:
                effective = 6 - score             // 反向计分
            ELSE:
                effective = score
            rawSum = rawSum + effective

        // 公式：转化分 = (原始分 - 条目数) / (条目数 × 4) × 100
        converted = (rawSum - n) / (n * 4) * 100
        converted = CLAMP(converted, 0, 100)      // 防御性边界
        resultScores[type] = {
            raw: rawSum,
            converted: converted,                 // 保留 2 位小数用于存储/展示
            measured: true,
            judgement: "NONE"
        }

    // 4. 平和质单独判定
    pinghe = resultScores[PINGHE].converted
    biasedTypes = 2..9 where resultScores[type].measured = true
    allBiasedBelow40 = ALL(type IN biasedTypes:
                          resultScores[type].converted < 40)

    IF pinghe is not null AND pinghe >= 60 AND allBiasedBelow40:
        main = PINGHE
        secondary = []
        tendency = biasedTypes where 30 <= converted < 40
        mark main as "PINGHE"
        mark tendency as "TENDENCY"
        RETURN result(main, secondary, tendency, resultScores)

    // 5. 偏颇体质判定
    biasedCandidates = biasedTypes where converted >= 40

    IF biasedCandidates is empty:
        main = UNDETERMINED (0)
        secondary = []
        tendency = biasedTypes where 30 <= converted < 40
        RETURN result(main, secondary, tendency, resultScores)

    // 6. 主体质：分数最高者；同分按固定枚举顺序（2..9）打破平局
    main = biasedCandidates
             .OrderByDescending(converted)
             .ThenBy(type enum order ascending)
             .First()

    // 7. 兼夹：其余所有 >= 40 的偏颇体质
    secondary = biasedCandidates
                  .Where(type != main)
                  .OrderByDescending(converted)
                  .Select(type)

    // 8. 倾向：30–39，排除主体质
    tendency = biasedTypes
                 .Where(type != main)
                 .Where(30 <= converted < 40)
                 .OrderByDescending(converted)
                 .Select(type)

    mark main as "MAIN"
    mark secondary as "SECONDARY"
    mark tendency as "TENDENCY"
    RETURN result(main, secondary, tendency, resultScores)

4.3 判定规则汇总#

条件结果
平和 ≥ 60，且其余八种均 < 40主体质 = 平和；兼夹为空；30–39 的其余体质记入倾向
平和 ≥ 60，但存在其他体质 ≥ 40不走平和；按偏颇体质规则判定
平和 < 60，存在偏颇体质 ≥ 40主体质 = 分数最高的偏颇体质；其余 ≥ 40 为兼夹；30–39 为倾向
平和 < 60，且没有偏颇体质 ≥ 40主体质 = 未判定（0）；30–39 为倾向；提示复测或咨询药师
某维度没有题目该维度 measured = false，不参与主体质/兼夹/倾向
全部维度低分主体质 = 未判定（0），不能默认判为平和

4.4 边界处理#

边界处理
未答题草稿允许；提交时若必答题缺失，返回 400 和缺失题号，不产生测评记录
某体质条目数为 0该维度 measured = false、converted = null；不参与判定；发布 TCM 问卷时要求九维都有题目，正常不会出现
全部低分主体质 0 未判定；不默认平和；返回提示“暂未判定，建议复测或咨询药师”
反向计分选项原始分 1–5，有效分 6 - 原始分；题干和选项文案保持原样，前端不反转
分数越界计算后 CLAMP(0, 100)；n > 0 保证分母不为 0
小数精度判定使用未舍入值，存储/展示保留 2 位小数，避免 39.995 四舍五入后误判
同分并列主体质按枚举顺序 2..9 取第一个；其余同分者进入兼夹
重复提交幂等返回已提交结果，不重复计分
并发提交事务内检查 Status = Draft 后更新；第二个请求读到已提交状态时返回已有结果
问卷版本变化草稿绑定原版本；提交仍按原版本计分；响应提示有新版本
药师录入使用同一计分服务，Source = 2，不改变判定规则

  • 管理端按权限码控制，访问写审计；
  • 通用 SystemOperationLogs 排除健康明文；
  • 日志、错误日志、接口响应不得输出完整健康文本；
  • 列表默认脱敏展示手机号（如 138****1234）。

v2 建议：

  • 对 AllergyHistory、MedicalHistory、CurrentMedications、AnswersJson 评估 SQL Server Always Encrypted 或应用层字段加密；
  • 密钥与数据库分离管理；
  • 增加保留期、匿名化、导出审批。

9. 风险与遗留问题#

风险说明建议
问卷版权/来源60 道题可能来自受版权保护的量表或出版物，直接录入代码/仓库有法律风险先确认授权来源；生产内容由管理员录入，代码不硬编码；保留 SourceName、CopyrightNotice
量表版本标准可能修订，评分规则和题目会变化用 ScaleCode + Version 固化；历史测评保存版本快照；新版本发布后旧版本归档
评分边界需医学确认平和判定、兼夹、倾向、同分、全部低分涉及医学解释由中医/药师确认规则与文案后再上线
通用操作日志泄露现有 AppDbContext 自动把健康字段写入 SystemOperationLogs实施前确认排除健康实体；专用审计表覆盖
同意与撤回撤回后历史数据删除/保留策略未定法务确认；v1 先停止新增，历史保留策略留到 v2
药师/客服角色现有管理端多为 AdminOnly，药师/客服可能没有 admin 角色确认角色模型；健康管理端用 AnyUser + 权限码
加密方式v1 仅 TDE/访问控制，数据库文件或备份仍可能含明文v2 评估 Always Encrypted / 应用层加密；密钥分离
测评不可变应用层禁止修改，但数据库管理员仍可直接改限制生产库权限；v2 可加触发器/审计对账
JSON 查询性能兼夹/分数 JSON 不利直接筛选主体质已单独列；v2 如分析需求增加投影表
草稿并发同一会员多设备同时编辑草稿v1 最后写入生效；v2 增加版本号/乐观锁
审计日志增长访问日志随管理端使用增长设定保留期、归档策略；v2 实现
成员资料重复会员表已有 Birthday/Gender，画像也有明确画像为准或首次同步；避免两处长期不一致
移动端写死文案个人中心当前写死“气虚夹湿型”v1 必须改为读取最近测评，未测评显示“未测评”
商品提示合规孕哺/过敏提示措辞不当可能被理解为医疗建议使用“请咨询药师/就医”表述，不做诊断性结论

10. 需要用户决策的开放问题#

  1. 问卷来源与版权：60 道题是否已有合法授权来源？生产环境是由管理员在后台录入，还是允许把授权后的题目作为种子数据放仓库？
  2. 药师/客服角色：现有系统里药师、客服对应哪些角色？是否同意健康管理端使用 AnyUser + 权限码，而不是继续用 AdminOnly？
  3. 同意文本与撤回策略：同意文案由谁定稿？撤回后历史健康数据是保留、匿名化还是删除？保留期多长？
  4. 未成年人：是否允许未成年人使用？如允许，是否需要监护人同意流程？
  5. 加密级别：v1 是否接受“TDE + 权限控制 + 日志脱敏”，把字段级加密放到 v2？还是要求 v1 就做 Always Encrypted？
  6. 变更日志粒度：原始答案 AnswersJson 在变更日志里存全文，还是只存题目数 + 哈希摘要？本方案默认后者。
  7. 药师可见范围：药师/客服查看测评时，是只看九项分数和主体质，还是可以看全部原始答案？本方案默认可以看，但查看详情需填写访问事由。
  8. 会员自查变更记录：v1 是否给会员开放自己的变更日志？本方案默认只给管理端审计权限。
  9. 会员性别/生日归属：画像表单独存 Gender/BirthDate，还是在读取时以 MallMembers 为准？本方案默认画像表存健康档案使用的值，首次可从会员资料带入。

  11. 草稿自动保存：v1 是否允许草稿逐题自动保存？本方案默认允许。
  12. 测评结果文案：主体质/兼夹/倾向的展示文案和“未判定”提示，由业务还是药师团队定稿？

商城促销与售后规则#

状态：有效 | 最后核对：2026-11-10 | 对应代码：web-api/src/QPS.Mall/Domain/Services/MallPromotionEngine.cs（促销引擎）、Application/Features/MallOrders/CreateMallOrderCommand.cs（下单校验）、web-api/src/QPS.Mall/Domain/MallAfterSaleRules.cs（售后约束）、Application/Features/MallRefunds、Application/Features/MallReturns（退款/退货流程）、admin/src/views/mall/promotion/index.vue（管理端促销配置）。

1. 统一模型#

每条促销由两个固定维度加一个动作构成：

促销 = 商品范围（Scope） + 订单门槛（ThresholdAmount） + 动作（Action）
  • 商品范围（ScopeType）：Global 全场 / Category 指定分类 / Product 指定商品 / Sku 指定规格。分类范围按祖先链匹配，选中父分类即覆盖其下子分类商品。
  • 订单门槛（ThresholdAmount，独立列）：范围内商品金额累计达到该值时促销生效，所有动作类型统一使用此门槛。
  • 门槛金额的计算口径：折扣、买赠、免运费按范围内商品原价合计判断；满减延后到应用阶段，按范围内行级折扣后的金额判断（见 3.1）。
  • 促销类型（PromotionType，int 列）：0 满减 / 1 折扣 / 2 买赠，仅用于列表筛选；真正参与计算的是 ActionType。

2. 动作类型（Action）#

类型actionType动作配置层级规则文本示例
满减DiscountAmount{ amount } 减免金额订单级满 ¥100 减 ¥20
折扣DiscountRate{ rate } 折扣比例（0.1~1）行级满 ¥100 打 8.0 折
买赠Gift{ skuId, quantity } 赠品规格与数量行级满 ¥100 赠 1 件赠品
免运费FreightFree{} 无参数订单级满 ¥100 免运费

FreightFree 已在引擎、动作策略与 DI 注册中落地（Actions.cs、DependencyInjection.cs），下单与预览会据 IsFreightFree 把运费置 0。但 MallPromotionType 枚举只有 0/1/2 三个值，管理端促销表单也只提供满减、折扣、买赠三项，因此当前无法从管理端创建免运费促销；新增入口时必须同步枚举、表单与校验。

3. 生效方式#

3.1 引擎自动应用#

促销独立生效，不依赖任何活动关联。MallPromotionEngine 分「匹配」与「应用」两个阶段：

匹配（Match）：按 CreatedAt → Id 固定顺序遍历，逐条过滤。

  1. 促销启用（IsActive）、未删除；
  2. 时间窗生效：StartDate 为空或 ≤ 当前时间，且 EndDate 为空或 > 当前时间（左闭右开）；
  3. 范围匹配：筛选订单中属于促销范围的订单项，无命中行直接跳过；
  4. 门槛判断：非满减动作按范围内原价合计 ≥ ThresholdAmount 才算命中；满减留到应用阶段判断。

应用（Apply）：顺序固定，不可调整。

  1. 行级折扣：逐行只取一条，优惠额最大者胜出；同额按作用范围具体度 Sku > Product > Category > Global，再按 CreatedAt、Id 稳定排序。
  2. 买赠：直接生效，不参与比价，生成 0 元赠品行（带 IsGift 标记与促销关联），可与折扣并存。
  3. 整单满减：门槛按各自覆盖范围内行级折扣后的金额判断，抵扣额取 min(amount, 范围内金额)；覆盖商品有交集的两条满减互斥，只取实际抵扣最大的一条；完全不重叠则各自生效。
  4. 免运费：直接生效，置 IsFreightFree。

满减与折扣/赠品可叠加；有交集的满减之间、同一行的折扣之间互斥。促销不做使用次数限制。

3.2 与活动的关系#

活动仅承担内容展示（封面、说明、富文本详情、时间窗口），不再关联促销，也不影响促销是否生效、不限制活动页商品范围。

5. 售后规则#

售后分「整单退款」与「退货退款」两条链路，都只按整单实付金额执行，不支持部分退款、部分退货。公共约束集中在 MallAfterSaleRules，退款/退货 Handler 不得各自实现校验。

对象流转触发

项目背景与业务链路#

状态：有效 | 最后核对：2026-11-10 | 对应代码：web-api/src/QPS.Crm、admin/src/views/crm

本文描述框架内置的示例业务（中药材供需撮合 CRM），用于演示模块化业务开发方式；通用框架定位与复用方式见 根目录 README。

1. 项目背景#

中药材采购涉及产地、品类、规格、质量、数量和交期等多项条件。供给方的基地、合作社和供应商掌握货源信息，需求方的药厂和采购企业维护采购需求；这些信息往往分散在线索、沟通记录和个人经验中，难以持续跟进、横向比较和复盘。

QPS 面向中药材供需双方的线索经营与撮合推进，先把双方的客户档案、供给条件、采购需求和沟通过程沉淀为可维护的业务数据，并支持业务人员人工筛选候选供给方、建立和推进撮合机会。

平台服务三类业务角色：

角色关注目标平台沉淀的核心信息
供给方让可供药材被及时发现和持续跟进基地主体、具体基地、供应品类、可供量、规格、质量条件、供货周期和价格预期
需求方获得符合生产计划的原料供给药企厂商、采购需求、采购明细、数量、规格、质量要求、交期和收货地
平台业务人员经营供需线索并推动合作联系人、负责人、沟通记录、待跟进事项、供需条件和业务状态

2. 平台定位#

QPS 是中药材供需信息标准化和客户跟进平台，不是现阶段的交易系统。

当前重点是让供给方和需求方的信息可以被持续维护、核实和跟进，并让两侧的品类及条件具备可比较的基础。平台为供需撮合提供数据与流程准备，但尚不替代撮合台账、报价、样品、合同、结算或交易管理。

3. 当下能做什么#

建立并经营供给方档案#

  • 维护基地主体及其名下的具体基地，记录地区、规模、来源和基础信息。
  • 维护基地联系人和主联系人，保留沟通记录、最近跟进结果和下一次跟进计划。
  • 分配和转移业务负责人，查看负责人流转记录，并在跟进任务工作台处理逾期、当日和未安排跟进的事项。

标准化管理供应信息#

  • 在具体基地维护供应信息，记录供应品类、可供量、单位、规格、质量条件、产新期、供货周期、价格预期和有效期。
  • 通过供应状态和有效期区分待确认、有效、暂停、已售罄或已失效的信息，避免将过期供给当作可用货源。
  • 供应品类使用统一的中药材品类字典，为供需比较和候选筛选建立共同口径。

建立并经营需求方档案#

  • 维护药企厂商档案、联系人、负责人和沟通记录。
  • 创建和维护采购需求及采购明细；一张需求可包含多个采购品类，并记录数量、单位、规格、质量要求、目标价格、交期和收货地。
  • 按需求状态维护从待确认到有效、匹配中、已完成或已关闭的业务过程，并保留关闭原因。

人工撮合与推进#

  • 以采购需求明细为入口，按品类、地区、可供量、规格、质量要求、供货周期和预期价格筛选有效供应信息。
  • 为一条采购需求明细建立撮合机会，并维护多个候选供应；候选可标记为待评估、保留、中选或淘汰，淘汰时必须说明原因。
  • 按匹配核实、商务沟通、意向确认三个阶段推进机会，记录下一步动作、说明和计划时间；可暂停、恢复或以撮合成功、未成交、需求取消关闭机会。

提供基础运营支撑#

  • 在工作台查看跟进漏斗、供给品类分布、供需线索新增趋势、厂商优先级和采购品类分布等基础图表。
  • 提供用户、角色、权限、行政区划、数据字典和操作日志等管理能力，支撑业务数据的可控维护。

4. 当前业务链路#

以下链路均为当前已具备的能力：

供给方：基地主体建档 -> 具体基地维护 -> 供应信息核实与维护 -> 联系人与跟进
需求方：药企厂商建档 -> 采购需求维护 -> 采购明细维护 -> 联系人与跟进
撮合：采购明细 -> 候选供应筛选 -> 撮合机会 -> 阶段推进与候选处置 -> 关闭归档
协同：负责人分配/流转 -> 跟进任务处理 -> 工作台查看基础运营情况

当前两侧数据层级为：

基地主体 -> 具体基地 -> 供应信息
药企厂商 -> 采购需求 -> 采购明细

供应信息中的供应品类，以及采购明细中的采购品类，是当前供需品类信息的唯一事实来源，也是人工筛选候选供给方的共同口径。

5. 目标业务闭环#

平台的完整目标是把已沉淀的供给与需求信息用于撮合推进，并对结果进行复盘：

供应信息 + 采购明细
        -> 候选供给方筛选
        -> 撮合机会推进
        -> 报价、样品、验收与谈判
        -> 成交或流失归档
        -> 复购机会与经营分析

当前系统已支持候选供给方筛选、撮合机会建立、候选处置和人工阶段推进；报价、样品、验收、合同、结算、成交归因和复购管理尚未形成独立业务模块。

6. 以后能做什么#

近期：撮合过程深化#

在既有候选筛选和撮合机会推进的基础上，补齐报价、样品、验收和谈判等过程记录，并形成可复盘的推进台账。

中期：成交与复购闭环#

记录成交、流失和失败原因，沉淀成交品类、合作规模和关键条件；基于已完成的撮合过程识别复购机会，让业务人员能够持续经营有效合作关系。

远期：供需数据化运营#

在撮合过程与结果数据积累后，建设匹配漏斗、转化率、品类供需和合作表现等看板，为品类经营、线索投入和业务决策提供依据。

7. 当前边界#

平台当前不提供自动推荐、报价与样品管理、合同结算、成交归因或复购管理。候选筛选结果由业务人员确认，撮合机会用于人工推进和关闭归档，不替代交易执行系统。
