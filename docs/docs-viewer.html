模块化单体架构#

基于 2026-11-07 的 web-api 代码整理。后端为 .NET 8 模块化单体：一个进程、一个数据库，按业务模块拆分项目，模块通过 AddQpsXxx() 显式启用。

1. 项目与职责#

项目职责关键内容
QPS.Shared与业务无关的公共契约和横切能力BaseEntity、ApiResponse、分页、JWT 配置、IUnitOfWork、IPermissionChecker、ICurrentUserService、PermissionAttribute、领域事件契约、三个 Pipeline Behaviour
QPS.System系统能力用户、角色、权限、数据字典、行政区、操作日志、错误日志；登录、权限检查器
QPS.CrmCRM 业务药材基地主体/基地/供应、联系人、跟进、流转、厂商、采购需求、撮合机会、业务活动
QPS.Mall商城业务商品/SKU/分类/标签/评价、购物车、订单/支付/退款/退货/发货、促销/优惠券/活动、会员/地址/积分、内容页
QPS.Persistence持久化基础设施单一 AppDbContext、三套模型配置、迁移、种子数据、CurrentUserService、JwtGenerator
QPS.Host组合根与 HTTP 基础设施Program.cs、上传控制器、响应包装过滤器、异常中间件、MVC/JWT/CORS/Swagger 注册

2. 依赖方向#

QPS.Host ──> Shared, System, Crm, Mall, Persistence
QPS.Persistence ──> Shared, System, Crm, Mall
QPS.Crm ──> Shared, System
QPS.Mall ──> Shared
QPS.System ──> Shared
QPS.Shared ──> 无业务模块依赖

约束由 web-api/tests/QPS.ArchitectureTests/ProjectReferenceTests.cs 和 ModuleBoundaryTests.cs 固化：

  • QPS.Shared 不引用任何业务模块或 Host。
  • QPS.System 不引用 Crm、Mall、Persistence、Host。
  • QPS.Crm 不引用 Mall、Persistence、Host。
  • QPS.Mall 不引用其他业务模块、Persistence、Host。
  • QPS.Persistence 不引用 Host。
  • Mall 的 Feature 不得直接引用其他 Feature 的 Handler。

3. 模块内分层#

业务模块（System / Crm / Mall）保持四层目录：

QPS.Xxx/
  Domain/          实体、值对象、领域服务、领域事件
  Application/     Features/<业务>/*Command|*Query|*Handler|*Validator
  Contracts/       模块对外的 DbContext 接口与 DTO
  Controllers/     HTTP 入口，只调用 IMediator
  • Domain：只依赖 QPS.Shared，不依赖 MediatR、EF Core 或 ASP.NET Core。
  • Application：按 Feature 垂直切分，一个用例一个 Handler；查询命名 XxxQuery，命令命名 XxxCommand。
  • Contracts：暴露 ISystemDbContext / ICrmDbContext / IMallDbContext 及 DTO，供 Persistence 实现、供 Controller 使用。
  • Controllers：不写业务逻辑，只把请求转成 Command/Query 并 Send。

QPS.Shared 分层：

Common/      BaseEntity、ApiResponse、PaginationRequest/Response、JwtOptions
Contracts/   IUnitOfWork、ICurrentUserService、IPermissionChecker、PermissionAttribute、
             IAllowAnonymousRequest、IDomainEvent、IDomainEventDispatcher、IJwtGenerator
Pipeline/    PermissionBehaviour、ValidationBehaviour、TransactionBehaviour、领域事件派发
Exceptions/  BusinessException、ValidationException 处理约定
Extensions/  通用扩展

QPS.Persistence 分层：

Database/        AppDbContext（同时实现 ISystemDbContext、ICrmDbContext、IMallDbContext、IUnitOfWork）
Configurations/  SystemModelConfiguration、CrmModelConfiguration、MallModelConfiguration
Identity/        CurrentUserService、JwtGenerator
Migrations/      EF Core 迁移
Seeds/           MallMockDataSeeder（仅 Development）

QPS.Host 分层：

Controllers/   FileUploadController、MemberFileUploadController
Filters/       ResponseWrapperFilter
Middleware/    ExceptionHandlerMiddleware
Registration/  ServiceRegistrationExtensions（MVC、CORS、Swagger、JWT）
Properties/    launchSettings.json（5000/5001）

4. 模块启用机制#

Program.cs 中的注册顺序：

  1. AddQpsMvc() + ConfigureQpsApplicationParts(typeof(Program).Assembly)
  2. AddQpsCors()、AddQpsSwagger()
  3. 读取并绑定 JwtOptions，AddQpsJwtAuthentication()
  4. AddQpsShared()
  5. AddQpsPersistence(configuration)
  6. AddQpsSystem(mvcBuilder)、AddQpsCrm(mvcBuilder)、AddQpsMall(mvcBuilder)

每个 AddQpsXxx() 做两件事：

  • 用 AddMediatR(cfg => cfg.RegisterServicesFromAssembly(...)) 注册本模块 Handler。
  • 把本模块程序集加入 MVC 的 ApplicationParts，暴露本模块 Controller。

ConfigureQpsApplicationParts 会先清空默认发现范围，再加入 Host 自身。因此未调用 AddQpsXxx() 的模块既不注册 Handler，也不暴露 Controller，ModuleRegistrationTests 对此有覆盖。

Mall 额外注册了促销策略与购物车处理器：

  • DiscountAmountAction、DiscountRateAction、GiftAction、FreightFreeAction
  • IActionStrategyRegistry、MallPromotionEngine、MallPromotionContextBuilder、MallPromotionPreviewService
  • MallCouponService、MallProductPromotionEnricher、GetMallCartHandler

5. Pipeline Behaviour 的真实约束#

三个 Behaviour 在 QPS.Shared/DependencyInjection.cs 中的注册顺序就是执行顺序，Permission 在最外层：

PermissionBehaviour  →  ValidationBehaviour  →  TransactionBehaviour  →  Handler

5.1 PermissionBehaviour#

  • 请求实现 IAllowAnonymousRequest，或 Endpoint 标记 [AllowAnonymous]：直接放行。
  • 已登录 member 角色且 Endpoint 使用 MallMember 策略：放行（移动端会员接口）。
  • 否则要求 ICurrentUserService.UserId 是有效 Guid，且用户 IsActive，否则抛出 401 BusinessException。
  • 从请求类型的 [Permission("...")] 读取权限码，缓存于 PermissionMetadataCache；无权限抛 403。
  • 权限判定链路：SystemUser.RoleId → SystemRolePermissions → SystemPermissions.Code。

约束：新增需要权限的接口时，把 [Permission] 标在 Command/Query 上，不要写在 Controller；Controller 只负责路由与 [Authorize] 策略。

5.2 ValidationBehaviour#

  • 收集当前请求类型的所有 IValidator<TRequest>，执行 FluentValidation。
  • 有错误时抛出 ValidationException，由 Host 的异常中间件统一转为业务错误响应。

约束：输入校验放 Validator，不在 Handler 里堆手写 if 判断；跨实体业务规则放 Domain。

5.3 TransactionBehaviour#

  • 请求类型名以 Query 结尾：直接 next()，查询不开启写事务。
  • 其余请求（Command）：BeginTransactionAsync → Handler → CommitAsync；异常时 RollbackAsync 后重抛。
  • AppDbContext.BeginTransactionAsync 内部有 Database.CurrentTransaction == null 判断，允许安全嵌套。

约束：

  • Handler 不得手写 BeginTransactionAsync / CommitAsync / RollbackAsync；需要事务的写操作必须命名为 XxxCommand。
  • Handler 可以按需调用 SaveChangesAsync；多步写入依赖外层事务保证原子性。
  • 只读逻辑命名为 XxxQuery，避免无意义的事务开销。

PipelineTests 强制约束：业务模块不得自己实现 IPipelineBehavior，三个通用 Behaviour 只能放在 QPS.Shared。

6. 持久化模型#

  • 全库只有 AppDbContext，同时实现三套模块契约与 IUnitOfWork。
  • OnModelCreating 依次应用 SystemModelConfiguration、CrmModelConfiguration、MallModelConfiguration，再挂软删除查询过滤器。
  • SaveChanges / SaveChangesAsync 统一处理：软删除、审计字段（CreatedAt/By、UpdatedAt/By）、操作日志。
  • BaseEntity 提供 Id、审计字段与 IsDeleted；业务代码不做物理删除，统一置 IsDeleted。
  • 除 SystemOperationLog、SystemErrorLog 外，删除均转为软删除。

7. HTTP 基础设施#

Program.cs 请求管道：

Swagger → CORS(AllowAll) → StaticFiles(wwwroot, /uploads 长缓存)
        → ExceptionHandlerMiddleware → Authentication → Authorization → MapControllers
  • ResponseWrapperFilter 把所有 Controller 返回值包装为 ApiResponse。
  • DataAnnotations 校验失败返回 HTTP 200 + { code: 400, msg }，与异常中间件格式一致。
  • JSON 使用 camelCase，中文不转义。
  • JWT 默认 FallbackPolicy 要求已认证；预置策略 AdminOnly（admin）、MallMember（member）、AnyUser。
  • 上传目录 wwwroot/uploads 启动时自动创建；/uploads 响应带一年 immutable 缓存头。

8. 新增模块/功能的检查清单#

  1. 新模块项目只引用 QPS.Shared（确需系统能力才引用 QPS.System），不得引用 Host/Persistence。
  2. 在 QPS.Host/Program.cs 调用 AddQpsXxx(mvcBuilder)，否则模块不会生效。
  3. 在 QPS.Persistence 增加 IXxxDbContext 实现与模型配置，并让 AppDbContext 实现该契约。
  4. 写操作命名 XxxCommand 并依赖全局事务；读操作命名 XxxQuery。
  5. 需要权限的请求加 [Permission]；公开接口实现 IAllowAnonymousRequest。
  6. 新增跨模块能力时通过 Contracts 接口，不直接引用其他模块内部实现。

权限设计方案#

本文档用于让后续开发者或 AI 快速理解 QPS 项目的权限设计。当前方案追求简单、直观、少封装。

核心原则#

权限码是唯一判断依据。

后端 SystemPermissions.Code 是权限来源，前端不再维护按钮权限映射表，也不再使用 BUTTONS.xxx 这类别名。

页面上需要控制权限的地方，直接写真实权限码：

<Permission code="CRM_HERB_BASE_CONTACT_PRIMARY">
  <el-button>设为主</el-button>
</Permission>

这样读页面时可以直接看到按钮受哪个权限控制。

前端实现#

前端使用 Permission 组件控制插槽显示：

admin/src/components/Permission/index.vue

组件职责只有一个：判断当前用户权限列表是否包含传入的 code。

页面用法：

<Permission code="SYSTEM_USER_ADD">
  <el-button type="primary">新增用户</el-button>
</Permission>

如果还需要业务条件，业务条件写在插槽内部：

<Permission code="CRM_HERB_BASE_CONTACT_PRIMARY">
  <el-button v-if="!row.isPrimary" type="primary" link>设为主</el-button>
</Permission>

不要恢复或新增 useAuthButtons 这类映射封装。

后端职责#

后端负责维护权限数据和登录后的权限返回。

主要职责：

1. 在初始化逻辑中维护标准权限。
2. 维护权限父子关系。
3. 按角色分配权限。
4. 清理废弃权限。
5. 登录后返回当前用户拥有的权限码列表。

废弃权限只应放在退休权限清理名单里，不应再次创建。

例如废弃的联系人无效功能权限：

CRM_HERB_BASE_CONTACT_INVALID

它只能用于历史数据清理，不能出现在标准权限和前端页面中。

角色策略#

admin 角色拥有完整权限。

初始化逻辑只保证普通 user 角色拥有以下入口：

HOME

因此普通用户默认不能进入基地或厂商管理。需要业务人员维护卖方和买方时，应由管理员为其授予 CRM_HERB_BASE、CRM_VENDOR 及对应操作权限。

厂商页面的新增、编辑、联系人、跟进记录和采购需求维护使用 CRM_VENDOR_ADD、CRM_VENDOR_EDIT、CRM_VENDOR_ASSIGN、CRM_PURCHASE_DEMAND_VIEW、CRM_PURCHASE_DEMAND_MANAGE 等权限控制；基地供应信息使用 CRM_HERB_BASE_SUPPLY_VIEW、CRM_HERB_BASE_SUPPLY_MANAGE；撮合机会页面入口和操作分别使用 CRM_MATCH_OPPORTUNITY_VIEW、CRM_MATCH_OPPORTUNITY_MANAGE。新增细粒度权限时，后端初始化、角色授权和前端 Permission 用法必须同步更新。

新增权限流程#

新增一个按钮权限时按以下流程：

  1. 后端新增标准权限码。
  2. 给需要的角色授权。
  3. 前端用 Permission 组件包裹按钮。
  4. 构建验证前端。

示例：

<Permission code="CRM_HERB_BASE_EXPORT">
  <el-button>导出</el-button>
</Permission>

不要新增前端权限映射，不要使用隐式拼接规则。

QPS 从 SQL Server 迁移到 SQLite 的可行性分析#

基于 2026-11-07 的 web-api 实际代码与迁移文件整理。EF Core 8.0.8，net8.0，单一 AppDbContext，49 个迁移，54 张表。本文只做分析，未改任何代码、库或迁移。

0. 结论#

推荐只做双 provider 支持，不推荐把生产库整体迁到 SQLite。

SQLite 适合开发、单元测试、单机演示和离线试用；生产环境继续使用 SQL Server。若强行整体替换，金额语义、大小写语义、迁移体系和并发写入这四块都需要实质性改造，且部分风险无法靠 SQLite 本身消除。

2.2 双 provider 并行的可行性#

可以并行，但不能让两套迁移共存在同一个程序集：EF 的 ModelSnapshot 与迁移历史只认一个 provider，混放会导致 snapshot 互相覆盖。两种可行结构：

  1. 生产 SQL Server 保留迁移；SQLite 仅用 EnsureCreated（推荐，成本最低）
    • SQL Server：MigrateAsync() + 现有 49 个迁移。
    • SQLite：Database.EnsureCreatedAsync()，不生成迁移；开发/测试库可从空库直接建表。
    • 代价：SQLite 无法享受增量迁移，每次模型变化要删库重建；仅适合开发/测试。
  2. 按 provider 拆迁移程序集

3. 金额与 decimal（本次最关键的阻断点之一）#

3.1 EF + SQLite 实际怎么存#

SQLite 没有 decimal 类型。EF Core 的 SQLite provider 默认把 decimal 映射为 TEXT，写入时按 invariant 字符串保存（如 "1234.56"）。迁移里的 decimal(18,2) 声明不会被 SQLite 执行，重新生成迁移后也不会保留精度语义。

后果分两类：

  • C# 侧读写是精确的：decimal → TEXT → decimal 往返不丢精度，领域层 MallOrder.CalculatePayableAmount、退款金额校验这些 C# 计算不受影响。
  • SQL 侧比较 / 排序 / 聚合是错的：
    • ORDER BY 按文本字典序："9.9" > "10.0"，金额排序会乱。
    • WHERE amount <= x 按文本比较，筛选结果错误。
    • SUM() 会把 TEXT 隐式转 REAL，产生浮点误差；MAX() 按文本比较。
    • TEXT 列上的索引对数值范围查询无效。

4. 迁移：改现有还是重新生成#

4.1 现有迁移不能直接复用#

49 个迁移全部由 SQL Server provider 生成，包含：

  • 列类型 nvarchar(...) 279 处、datetime2 137 处、decimal(18,2) 48 处
  • 裸 SQL 52 处，其中 GETDATE() 23、NEWID() 19、TOP ( 13、IF EXISTS 1
  • 索引过滤条件 [IsDeleted] = 0，以及 1 处 N'推进中'
  • Designer 文件里的 SQL Server 模型注解

6. 并发与事务#

6.1 现状#

  • 所有 Command 经 TransactionBehaviour 自动 BeginTransaction / Commit / Rollback（TransactionBehaviour.cs:24-33）。
  • 关键写路径：
    • 下单：CreateMallOrderCommand 在一个事务里做库存条件扣减（2 次 ExecuteUpdateAsync）、写订单/明细/流水。
    • 领券：MallCouponService 两次 ExecuteUpdateAsync（领券计数 + 会员券）。
    • 支付/退款/超时关单：MallOrderResolver 条件更新 + 库存回补，均在同一事务内。

6.2 SQLite 行为#

  • 单写锁：同一时刻只允许一个写事务；WAL 模式下读可以并发，写仍串行。
  • 事务从首次写入一直持锁到提交；上面的下单/退款事务包含多次写，锁持有时间会被放大。
  • Microsoft.Data.Sqlite 默认有 busy timeout（约 30 秒），但高并发下仍会出现 database is locked；开启 WAL 只能缓解读，不解决写排队。
  • 没有重试策略：TransactionBehaviour 没有 ExecutionStrategy 重试，SQLite 锁冲突会直接冒到接口。

6.3 判断#

场景判断
单实例、开发/测试、并发写 < 5/s、数据量 < 几十万行可接受（建议 journal_mode=WAL、busy_timeout=5000、缩短事务）
生产多用户下单、秒杀、支付回调峰值、多实例部署不可接受：写入串行化会直接成为瓶颈，且 database is locked 无法通过扩容解决
支付回调幂等单写锁反而降低并发竞争，但没有乐观并发/唯一幂等键时，仍可能重复更新；与 provider 无关

7. 软删除、审计、操作日志#

  • 全局查询过滤器 HasQueryFilter(e => !e.IsDeleted) 在 AppDbContext.OnModelCreating 中统一注册，属于 EF 模型层，SQLite 下行为一致。
  • 软删除、审计字段填充依赖 SaveChanges 拦截器/领域事件，均在 C# 侧执行，与 provider 无关。
  • 操作日志：系统在 SaveChanges 时为变更实体批量写日志。SQLite 下这些写入与业务写入在同一事务里，日志量越大事务越长，锁持有越久；表本身无上限增长，SQLite 文件会持续变大且难以在线收缩。
  • 差异点只有一个：过滤唯一索引依赖 HasFilter，SQLite 下需去掉 N'…' 并确认方括号写法；其余无行为差异。

促销 = 商品范围（Scope） + 订单门槛（ThresholdAmount） + 动作（Action）
  • 商品范围（ScopeType）：Global 全场 / Category 指定分类 / Product 指定商品 / Sku 指定规格。
  • 订单门槛（ThresholdAmount，独立列）：范围内商品金额累计达到该值时促销生效，三种促销类型统一使用此门槛。
  • 门槛金额的计算口径：按范围内商品的订单金额累计；范围选 Global 时按全订单金额计算。

2. 三种促销类型（Action）#

类型actionType动作配置规则文本示例
满减DiscountAmount{ amount } 减免金额满 ¥100 减 ¥20
折扣DiscountRate{ rate } 折扣比例（0.1~1）满 ¥100 打 8.0 折
买赠Gift{ skuId, quantity } 赠品规格与数量满 ¥100 赠 1 件赠品

3. 生效方式#

3.1 引擎自动应用#

促销独立生效，不依赖任何活动关联。MallPromotionEngine 在计算订单价格时自动匹配并应用：

  1. 促销启用、未删除、在促销自身时间范围内、未超出每人/每单使用次数限制；
  2. 范围匹配：筛选订单中属于促销范围的订单项；
  3. 门槛判断：范围内商品金额合计 ≥ ThresholdAmount；
  4. 满减直接减金额，折扣按比例折算，买赠生成 0 元赠品订单项（带 IsGift 标记与促销关联）。

3.2 与活动的关系#

活动仅承担内容展示（封面、说明、富文本详情、时间窗口），不再关联促销，也不影响促销是否生效、不限制活动页商品范围。

项目背景#

中药材采购涉及产地、品类、规格、质量、数量和交期等多项条件。供给方的基地、合作社和供应商掌握货源信息，需求方的药厂和采购企业维护采购需求；这些信息往往分散在线索、沟通记录和个人经验中，难以持续跟进、横向比较和复盘。

QPS 面向中药材供需双方的线索经营与撮合推进，先把双方的客户档案、供给条件、采购需求和沟通过程沉淀为可维护的业务数据，并支持业务人员人工筛选候选供给方、建立和推进撮合机会。

平台服务三类业务角色：

角色关注目标平台沉淀的核心信息
供给方让可供药材被及时发现和持续跟进基地主体、具体基地、供应品类、可供量、规格、质量条件、供货周期和价格预期
需求方获得符合生产计划的原料供给药企厂商、采购需求、采购明细、数量、规格、质量要求、交期和收货地
平台业务人员经营供需线索并推动合作联系人、负责人、沟通记录、待跟进事项、供需条件和业务状态

平台定位#

QPS 是中药材供需信息标准化和客户跟进平台，不是现阶段的交易系统。

当前重点是让供给方和需求方的信息可以被持续维护、核实和跟进，并让两侧的品类及条件具备可比较的基础。平台为供需撮合提供数据与流程准备，但尚不替代撮合台账、报价、样品、合同、结算或交易管理。

当下能做什么#

建立并经营供给方档案#

  • 维护基地主体及其名下的具体基地，记录地区、规模、来源和基础信息。
  • 维护基地联系人和主联系人，保留沟通记录、最近跟进结果和下一次跟进计划。
  • 分配和转移业务负责人，查看负责人流转记录，并在跟进任务工作台处理逾期、当日和未安排跟进的事项。

标准化管理供应信息#

  • 在具体基地维护供应信息，记录供应品类、可供量、单位、规格、质量条件、产新期、供货周期、价格预期和有效期。
  • 通过供应状态和有效期区分待确认、有效、暂停、已售罄或已失效的信息，避免将过期供给当作可用货源。
  • 供应品类使用统一的中药材品类字典，为供需比较和候选筛选建立共同口径。

建立并经营需求方档案#

  • 维护药企厂商档案、联系人、负责人和沟通记录。
  • 创建和维护采购需求及采购明细；一张需求可包含多个采购品类，并记录数量、单位、规格、质量要求、目标价格、交期和收货地。
  • 按需求状态维护从待确认到有效、匹配中、已完成或已关闭的业务过程，并保留关闭原因。

人工撮合与推进#

  • 以采购需求明细为入口，按品类、地区、可供量、规格、质量要求、供货周期和预期价格筛选有效供应信息。
  • 为一条采购需求明细建立撮合机会，并维护多个候选供应；候选可标记为待评估、保留、中选或淘汰，淘汰时必须说明原因。
  • 按匹配核实、商务沟通、意向确认三个阶段推进机会，记录下一步动作、说明和计划时间；可暂停、恢复或以撮合成功、未成交、需求取消关闭机会。

提供基础运营支撑#

  • 在工作台查看跟进漏斗、供给品类分布、供需线索新增趋势、厂商优先级和采购品类分布等基础图表。
  • 提供用户、角色、权限、行政区划、数据字典和操作日志等管理能力，支撑业务数据的可控维护。

当前业务链路#

以下链路均为当前已具备的能力：

供给方：基地主体建档 -> 具体基地维护 -> 供应信息核实与维护 -> 联系人与跟进
需求方：药企厂商建档 -> 采购需求维护 -> 采购明细维护 -> 联系人与跟进
撮合：采购明细 -> 候选供应筛选 -> 撮合机会 -> 阶段推进与候选处置 -> 关闭归档
协同：负责人分配/流转 -> 跟进任务处理 -> 工作台查看基础运营情况

当前两侧数据层级为：

基地主体 -> 具体基地 -> 供应信息
药企厂商 -> 采购需求 -> 采购明细

供应信息中的供应品类，以及采购明细中的采购品类，是当前供需品类信息的唯一事实来源，也是人工筛选候选供给方的共同口径。

目标业务闭环#

平台的完整目标是把已沉淀的供给与需求信息用于撮合推进，并对结果进行复盘：

供应信息 + 采购明细
        -> 候选供给方筛选
        -> 撮合机会推进
        -> 报价、样品、验收与谈判
        -> 成交或流失归档
        -> 复购机会与经营分析

当前系统已支持候选供给方筛选、撮合机会建立、候选处置和人工阶段推进；报价、样品、验收、合同、结算、成交归因和复购管理尚未形成独立业务模块。

以后能做什么#

近期：撮合过程深化#

在既有候选筛选和撮合机会推进的基础上，补齐报价、样品、验收和谈判等过程记录，并形成可复盘的推进台账。

中期：成交与复购闭环#

记录成交、流失和失败原因，沉淀成交品类、合作规模和关键条件；基于已完成的撮合过程识别复购机会，让业务人员能够持续经营有效合作关系。

远期：供需数据化运营#

在撮合过程与结果数据积累后，建设匹配漏斗、转化率、品类供需和合作表现等看板，为品类经营、线索投入和业务决策提供依据。

当前边界#

平台当前不提供自动推荐、报价与样品管理、合同结算、成交归因或复购管理。候选筛选结果由业务人员确认，撮合机会用于人工推进和关闭归档，不替代交易执行系统。

命名规则#

  • 目录名、文件名一律小写英文 kebab-case（[a-z0-9-]），中文只保留在文档第一行 H1 与索引链接文字里。
  • 例外：docs/archive/ 下的历史文件保留原文件名（含中文与日期前缀），只做移动、不改名。
  • 长期事实文档用 <topic>.md，不带日期、版本、状态后缀。
  • 接口契约用 <module>-<scope>-api.md；页面规格用 <page>-spec.md。
  • ADR 用 adr-0001-<slug>.md，编号 4 位、只增不减。
  • 归档文件保留原名与 YYYY-MM-DD- 前缀，正文不改。
  • 禁止出现大写字母、下划线、空格，以及「最终 / 新版 / 最新 / v2 / -old / 副本」等后缀。

写作约定#

  • 每份长期文档第 1 行为 # 标题，第 3 行为元信息块：> 状态：有效 | 最后核对：YYYY-MM-DD | 对应代码：路径。
  • 同一事实只维护一处，其他地方写「见 文档名」，不复述表格或命令。
  • 正文最多 3 级标题，一级小节用 ## 1. 编号。
  • 引用其他文档一律使用相对路径 Markdown 链接。
