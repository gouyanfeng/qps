本地启动与发布#

基于 2026-11-07 的仓库结构与 QPS.Host 配置整理。所有命令均以 E:\Code\QPS 为根目录。

1. 环境要求#

依赖要求
.NET SDK8.0（QPS.Host.csproj 目标框架 net8.0）
SQL Server本地实例；默认连接串指向 localhost 的 QPS_CRM 库
Node.js / npm管理端与移动端均使用 package-lock.json（npm）
EF Core CLI仅生产手动迁移需要，版本 8.x

2. 端口与地址#

服务地址说明
后端 HTTPhttp://localhost:5000launchSettings.json 默认绑定
后端 HTTPShttps://localhost:5001同上
Swaggerhttp://localhost:5000/swaggerDevelopment 下可直接访问
管理端http://127.0.0.1:5173Vite strictPort，被占用时直接报错，不会自动换端口
移动端 H5http://127.0.0.1:5174同上

后端 launchSettings.json 已设置 ASPNETCORE_ENVIRONMENT=Development，因此本地 dotnet run 默认进入开发模式。

3. 数据库#

3.1 连接串#

web-api/src/QPS.Host/appsettings.json：

Server=localhost;Database=QPS_CRM;User Id=sa;Password=123456;TrustServerCertificate=True;Encrypt=False;

生产环境不要改仓库内文件，使用环境变量覆盖：

ConnectionStrings__DefaultConnection=Server=...;Database=...;User Id=...;Password=...;

3.2 Development：自动迁移 + 示例数据#

QPS.Host/Program.cs 在 IsDevelopment() 时：

  1. 用 CreateExecutionStrategy() 包裹 Database.MigrateAsync()，启动即把数据库迁到最新版本。
  2. 从 ContentRoot 向上查找 mobile/src/mock 目录，执行 MallMockDataSeeder.SeedAsync 导入商城示例数据；目录不存在时只记录警告。

因此本地首次启动前只需保证 SQL Server 可连接，不需要手动建表。

3.3 Production：手动迁移#

非 Development 分支只执行 Database.CanConnectAsync()，不会自动建库或迁移。发布前必须手动执行：

cd E:\Code\QPS\web-api
dotnet ef database update `
  --project src/QPS.Persistence `
  --startup-project src/QPS.Host

需要交给 DBA 执行时，生成 SQL 脚本：

dotnet ef migrations script `
  --project src/QPS.Persistence `
  --startup-project src/QPS.Host `
  -o migrations.sql

新增迁移：

dotnet ef migrations add <MigrationName> `
  --project src/QPS.Persistence `
  --startup-project src/QPS.Host

首次使用 EF 工具：

dotnet tool install --global dotnet-ef --version 8.*

4. 后端启动#

cd E:\Code\QPS\web-api
dotnet restore QPS.sln
dotnet build QPS.sln -m:1
dotnet run --project src/QPS.Host
  • -m:1 限制 MSBuild 并行度，避免多项目并发编译占满内存；机器内存充足时可去掉，但本仓库默认建议保留。
  • 启动入口是 src/QPS.Host，不是旧的 src/4.QPS.WebAPI。
  • 控制器按模块注册：AddQpsSystem / AddQpsCrm / AddQpsMall 未调用时，对应模块的 Handler 与 Controller 都不生效。

测试#

dotnet test tests/QPS.UnitTests/QPS.UnitTests.csproj -m:1
dotnet test tests/QPS.ArchitectureTests/QPS.ArchitectureTests.csproj -m:1

QPS.ArchitectureTests 校验项目依赖方向、模块启用、Pipeline 归属与控制器策略，改动模块边界后必须跑。

5. 管理端#

cd E:\Code\QPS\admin
npm ci
npm run dev
  • 开发地址 http://127.0.0.1:5173。
  • .env 中 VITE_API_URL=http://localhost:5000/api，admin/src/api/index.ts 以此为 axios baseURL；未配置时回退 http://localhost:5000/api。
  • 生产构建：
npm run build

build 先执行 vue-tsc -b 类型检查，再执行 vite build；类型错误会阻断构建。

6. 移动端 H5#

cd E:\Code\QPS\mobile
npm ci
npm run dev:h5
  • 开发地址 http://127.0.0.1:5174。
  • H5 代码读取 VITE_API_BASE_URL（src/utils/http.ts、src/api/index.ts），未设置时回退 http://localhost:5000。
  • 当前 .env 写的是 VITE_API_URL，该变量不会被 H5 的 HTTP 层读取；需要指定后端时，在 .env.local 中设置 VITE_API_BASE_URL=http://localhost:5000。
  • 生产构建：
npm run build:h5

package.json 还保留微信/支付宝等小程序构建脚本，当前主要使用 H5。

7. 生产发布#

7.1 后端#

cd E:\Code\QPS\web-api
dotnet publish src/QPS.Host -c Release -o ./publish

发布前/后检查：

  1. 目标环境设置 ASPNETCORE_ENVIRONMENT=Production。
  2. 通过环境变量提供 ConnectionStrings__DefaultConnection 与 Jwt__SecretKey / Jwt__Issuer / Jwt__Audience。
  3. 先执行 3.3 的 dotnet ef database update，再启动进程。
  4. 确保进程对 wwwroot/uploads 有读写权限；目录在启动时自动创建。
  5. Production 不会导入 mobile/src/mock 示例数据。

启动：

$env:ASPNETCORE_ENVIRONMENT="Production"
dotnet .\publish\QPS.Host.dll

或由 IIS / 反向代理承载 publish 目录，按实际承载方式配置进程模型与端口。

7.2 前端#

cd E:\Code\QPS\admin
npm run build
# 产物在 admin/dist

cd E:\Code\QPS\mobile
npm run build:h5
# 产物在 mobile/dist/build/h5

部署前确认构建时的 VITE_API_URL / VITE_API_BASE_URL 指向生产 API，而不是 localhost:5000。

8. 常见问题#

现象排查
dotnet build 内存占用高或失败使用 -m:1，关闭并行构建与其他占用内存的进程
5000/5173/5174 启动失败端口被占用；前端 strictPort 不会自动换端口，先确认占用进程
启动时报数据库连接失败检查 SQL Server 实例、DefaultConnection、账号密码与 TrustServerCertificate
生产启动后表结构缺失Production 只做 CanConnectAsync，需先手动 database update
登录返回 401检查 Jwt 三个配置项是否完整，以及请求是否携带 Bearer Token
移动端请求打到错误地址检查 VITE_API_BASE_URL；.env 中的 VITE_API_URL 对 H5 不生效
本地没有商城示例数据确认 mobile/src/mock 存在，且环境为 Development
接口 403请求类型上是否有正确的 [Permission]，当前用户角色是否拥有该权限码

5.7 MallCartItem 结构（合表后）#

购物车已合表：不再保留车头，只保留明细行；没有任何明细即视为空购物车。

字段类型说明

约束与行为：

  • 唯一索引 (UserId, SkuId)，过滤条件 [IsDeleted] = 0。

  • SetQuantity(quantity) 覆盖数量，quantity <= 0 抛 BusinessException(400)。

5. Pipeline Behaviour 的真实约束#

三个 Behaviour 在 QPS.Shared/DependencyInjection.cs 中的注册顺序就是执行顺序，Permission 在最外层：

PermissionBehaviour  →  ValidationBehaviour  →  TransactionBehaviour  →  Handler

5.1 PermissionBehaviour#

  • 请求实现 IAllowAnonymousRequest，或 Endpoint 标记 [AllowAnonymous]：直接放行。
  • 已登录 member 角色且 Endpoint 使用 MallMember 策略：放行（移动端会员接口）。
  • 否则要求 ICurrentUserService.UserId 是有效 Guid，且用户 IsActive，否则抛出 401 BusinessException。
  • 从请求类型的 [Permission("...")] 读取权限码，缓存于 PermissionMetadataCache；无权限抛 403。
  • 权限判定链路：SystemUser.RoleId → SystemRolePermissions → SystemPermissions.Code。

约束：新增需要权限的接口时，把 [Permission] 标在 Command/Query 上，不要写在 Controller；Controller 只负责路由与 [Authorize] 策略。

5.2 ValidationBehaviour#

  • 收集当前请求类型的所有 IValidator<TRequest>，执行 FluentValidation。
  • 有错误时抛出 ValidationException，由 Host 的异常中间件统一转为业务错误响应。

约束：输入校验放 Validator，不在 Handler 里堆手写 if 判断；跨实体业务规则放 Domain。

5.3 TransactionBehaviour#

  • 请求类型名以 Query 结尾：直接 next()，查询不开启写事务。
  • 其余请求（Command）：BeginTransactionAsync → Handler → CommitAsync；异常时 RollbackAsync 后重抛。
  • AppDbContext.BeginTransactionAsync 内部有 Database.CurrentTransaction == null 判断，允许安全嵌套。

约束：

  • Handler 不得手写 BeginTransactionAsync / CommitAsync / RollbackAsync；需要事务的写操作必须命名为 XxxCommand。
  • Handler 可以按需调用 SaveChangesAsync；多步写入依赖外层事务保证原子性。
  • 只读逻辑命名为 XxxQuery，避免无意义的事务开销。

PipelineTests 强制约束：业务模块不得自己实现 IPipelineBehavior，三个通用 Behaviour 只能放在 QPS.Shared。

6. 持久化模型#

  • 全库只有 AppDbContext，同时实现三套模块契约与 IUnitOfWork。
  • OnModelCreating 依次应用 SystemModelConfiguration、CrmModelConfiguration、MallModelConfiguration，再挂软删除查询过滤器。
  • SaveChanges / SaveChangesAsync 统一处理：软删除、审计字段（CreatedAt/By、UpdatedAt/By）、操作日志。
  • BaseEntity 提供 Id、审计字段与 IsDeleted；业务代码不做物理删除，统一置 IsDeleted。
  • 除 SystemOperationLog、SystemErrorLog 外，删除均转为软删除。

7. HTTP 基础设施#

Program.cs 请求管道：

Swagger → CORS(AllowAll) → StaticFiles(wwwroot, /uploads 长缓存)
        → ExceptionHandlerMiddleware → Authentication → Authorization → MapControllers
  • ResponseWrapperFilter 把所有 Controller 返回值包装为 ApiResponse。
  • DataAnnotations 校验失败返回 HTTP 200 + { code: 400, msg }，与异常中间件格式一致。
  • JSON 使用 camelCase，中文不转义。
  • JWT 默认 FallbackPolicy 要求已认证；预置策略 AdminOnly（admin）、MallMember（member）、AnyUser。
  • 上传目录 wwwroot/uploads 启动时自动创建；/uploads 响应带一年 immutable 缓存头。

8. 新增模块/功能的检查清单#

  1. 新模块项目只引用 QPS.Shared（确需系统能力才引用 QPS.System），不得引用 Host/Persistence。
  2. 在 QPS.Host/Program.cs 调用 AddQpsXxx(mvcBuilder)，否则模块不会生效。
  3. 在 QPS.Persistence 增加 IXxxDbContext 实现与模型配置，并让 AppDbContext 实现该契约。
  4. 写操作命名 XxxCommand 并依赖全局事务；读操作命名 XxxQuery。
  5. 需要权限的请求加 [Permission]；公开接口实现 IAllowAnonymousRequest。
  6. 新增跨模块能力时通过 Contracts 接口，不直接引用其他模块内部实现。

4.6 风险与缓解#

风险：新会话或子代理只加载根 AGENTS.md，不点索引链接时，五条硬约束会成为“索引里有、脑子里没有”的盲区，最典型的后果是手写事务、漏掉软删除过滤、直接读实时商品表、绕过 [Permission]。

缓解措施（全部写进批次 4 的验收）：

  1. 标签区分：硬约束所在文件一律 必读，且在“说明”列直接写出主题词（构建、迁移、事务、索引、快照、权限），不写“运维说明”这类泛词。
  2. 各端首屏重复关键约束：web-api/AGENTS.md、admin/AGENTS.md、mobile/AGENTS.md 前 5 行各列 2–3 条与本端最相关的硬约束，并附根 AGENTS 索引链接。这是“单一事实源”的唯一允许例外：子目录 AGENTS 会被工具自动加载，重复是兜底，不是并列权威。
  3. 顺序与可检索：索引表按“必读在前、选读在后”排列；必读行的说明列必须出现关键词，便于脚本与人工 grep 校验。
  4. 机械校验：批次 4 增加检查项——根 AGENTS 只有一张表、无表格外正文；必读 行覆盖 5 类硬约束关键词；任一缺失即视为迁移未完成。
  5. 残余风险：若模型完全不读链接也不读子目录 AGENTS，仍会漏；此时以“构建/运行报错”暴露，需在 web-api/AGENTS.md 首屏保留 -m:1 与事务禁令两条最易踩的规则。

页面概念现有数据

映射规则：

  • ROOT 为树根，不在矩阵中显示、不可编辑；保存时按该角色原有状态保留（admin 含 ROOT，user 不含），避免改动存量语义。
  • ROOT 的直接 Menu 子节点 = 模块分组（CRM管理 / 商城管理 / 系统设置 / 首页）。
  • 分组内的 Menu 后代节点 = 矩阵的「页面行」；页面行的 Button 子节点 = 「操作按钮授权」单元格。
  • 顶层 Menu 若没有子菜单（如首页、商城管理），直接作为页面行展示。
  • 保存集合 = 勾选的页面 Menu + 勾选的 Button + 自动补齐的祖先 Menu + 保留的 ROOT。勾选任一按钮会自动带上其页面与模块，保证菜单路由可见。

3. 两栏职责与联动路径#

  1. 矩阵区：顶部模块筛选 chips + 行搜索 + 「全部展开 / 全部收起」+「全选访问」；主体为矩阵表格：
    • 分组行：模块名 + code，右侧三态全选框（全选/半选/未选，作用于该组所有页面行的访问开关）。
    • 页面行：页面名 + code（mono 小字），「页面访问权限」列是开关，右侧为该页面的按钮 chips。
  2. 右栏｜修改记录：相对已保存集合的实时 diff，卡片标注「新增授权 / 取消授权」+ 路径 + code；顶部显示待保存数量与「撤销所有」；保存后清空。

联动路径：

  • 角色切换入口只保留顶部角色下拉（不设左栏角色列表，也无下拉与列表的双向同步）→ 选择后载入该角色勾选态到矩阵与右栏 diff 基准。
  • 切换角色：载入新角色权限，未保存变更直接丢弃（与现有行为一致）。
  • 勾选页面开关 → 关闭时自动取消并锁定该页按钮（按钮 chips 进入只读态），同时刷新右栏 diff；打开时不自动勾选按钮。
  • 勾选按钮 → 自动同时勾选其页面与祖先模块（只影响展示与保存集合，不产生额外 diff 卡片以外的节点）。
  • 模块 chip / 搜索 → 只过滤当前展示的行，不影响已勾选集合与 diff 计算。
  • 重置 / 撤销所有 → 恢复到该角色已保存集合；保存 → PUT 成功后以当前集合为新基准。

4. 矩阵控件形态#

  • 全选（分组行）：el-checkbox 三态。组内页面全选 = 选中；部分 = indeterminate 半选；点击半选/未选 = 全选该组页面的「页面访问」；点击已选 = 全部取消（并联动清空按钮）。
  • 页面访问开关：el-switch，开=「允许访问」（主色 #009688），关=「已禁用」（灰色）；页面关闭时整行按钮区降透明度并锁定。
  • 按钮单元格：el-checkbox 内联流式排列，文案使用权限名称；code 以 tooltip 展示。删除类（code 结尾 _DELETE）加「高危」红色小标签，但仍可授权（现有系统没有后端锁定策略，不做假只读）。
  • 只读态：仅两种：ROOT 不可见/不可编辑；页面关闭后其按钮 chips 与组内联动处于 disabled。不引入角色级只读。
  • 空态：过滤后无命中显示「没有匹配的权限」；角色无权限时矩阵照常可操作。
