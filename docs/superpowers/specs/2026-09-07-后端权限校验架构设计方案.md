# 后端权限校验架构设计方案

**日期：** 2026-09-07
**状态：** 已实施，已完成验证

## 1. 目标

统一 QPS 后端的功能权限校验入口，减少各业务模块在 Handler 中重复查询用户、角色和角色权限的代码，同时保持业务代码干净、职责单一。

本方案只处理“当前用户是否可以执行此功能”。资源存在性、业务状态迁移、数据范围和领域规则继续由 Handler 或领域实体负责，不能迁入通用权限组件。

## 2. 当前问题

现有撮合机会模块通过 `CrmMatchOpportunityAuthorization` 在各个 Handler 中手工调用 `EnsureViewAsync` 或 `EnsureManageAsync` 校验权限。这种方式能工作，但存在以下问题：

- 每个新模块都可能复制用户、角色、权限查询和异常处理。
- 同一权限码的校验逻辑分散，后续容易出现漏校验或行为不一致。
- Handler 同时承担业务编排和通用权限基础设施职责，业务代码不够聚焦。

## 3. 方案选择

### 3.1 推荐方案：MediatR 权限行为

在 `QPS.Application` 中以请求类型特性声明功能权限，并通过 MediatR Pipeline Behavior 在进入 Handler 前统一校验。

优点：

- 权限码作为 Query、Command 的类型元数据声明，可直接阅读和审查。
- 所有 CQRS 请求共用一套校验逻辑，不在每个 Handler 中重复实现。
- 权限校验发生在参数验证和事务行为之前，拒绝请求不会进入后续应用层处理。
- Handler 只保留业务状态、资源关系、数据范围和领域规则，边界清晰。

### 3.2 不采用普通 HTTP 中间件

认证仍由 ASP.NET Core 认证中间件处理。普通中间件适合按请求路径和 HTTP 方法处理横切能力，但功能权限不应维护“路由 -> 权限码”映射：

- 一个 Controller 下可能有多个权限不同的动作。
- 同一应用请求可能由不同入口调用，权限应绑定应用请求语义，而非 URL。
- 路由映射会把权限规则分散到 WebAPI 层，无法随 Query、Command 一起审查。

因此不新增 URL 权限中间件。ASP.NET Core 的认证和授权链路保持现状，应用层功能权限由 MediatR 行为统一处理。

### 3.3 不采用 Handler 手工调用

Handler 手工调用权限助手只作为迁移期间的兼容方式。完成某个模块迁移后，应删除该模块的专用权限助手和 Handler 中的手工权限查询。

## 4. 职责边界

| 层级 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| ASP.NET Core Authentication Middleware | 验证 Token、建立用户身份与 Claims。 | 功能权限、业务状态、数据范围。 |
| WebAPI Controller | 接收 HTTP 请求、映射到 Query/Command、返回结果。 | 查询角色权限、维护状态机。 |
| `PermissionBehaviour` | 校验登录用户有效性及单个功能权限码。 | 查询业务对象、判断对象归属、判断状态是否可流转。 |
| Handler | 资源存在性、业务数据范围、用例编排、调用领域方法。 | 重复查询角色与权限关系。 |
| Domain Entity / Policy | 聚合内部不变量、状态迁移及领域规则。 | 当前 HTTP 用户的角色权限查询。 |

**业务状态必须仍由 Handler/领域规则处理。** 例如采购需求是否有效、撮合机会是否已经关闭、候选是否可追加、采购明细是否被引用，都属于业务状态或领域关系，必须保留在对应 Handler、领域实体或 Policy 中。`PermissionBehaviour` 不得通过权限校验结果改变业务状态，也不得承担状态机逻辑。

## 5. 目标组件

### 5.1 请求权限特性

在 `QPS.Application` 定义仅能标记在 Query、Command 类型上的单权限特性：

```csharp
[AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = false)]
public sealed class PermissionAttribute : Attribute
{
    public PermissionAttribute(string permissionCode) =>
        PermissionCode = permissionCode;

    public string PermissionCode { get; }
}
```

需要权限的 Query 或 Command 通过特性声明唯一权限码：

```csharp
[Permission(SystemPermissionCodes.CRM_MATCH_OPPORTUNITY_VIEW)]
public sealed record GetCrmMatchOpportunitiesQuery(...) :
    IRequest<PaginationResponse<CrmMatchOpportunityDto>>;
```

特性参数只能使用编译期常量，因此权限码统一由 `SystemPermissionCodes` 定义为 `const string`。常量名必须与权限码字符串完全一致，例如 `CRM_MATCH_OPPORTUNITY_VIEW = "CRM_MATCH_OPPORTUNITY_VIEW"`，不使用 PascalCase 二次命名。首期每个请求只声明一个权限码。多权限任一满足、全部满足、动态表达式和资源级 ACL 均不在本次范围内，避免过早泛化。

权限码不得在 Query、Command 或 Handler 中重复写字符串字面量。统一在 `QPS.Application.Features.System.SystemPermissionCodes` 定义常量，迁移撮合模块时将 `CRM_MATCH_OPPORTUNITY_VIEW`、`CRM_MATCH_OPPORTUNITY_MANAGE` 移入该类，后续模块按同一规则新增。

### 5.2 `PermissionBehaviour<TRequest, TResponse>`

在 `QPS.Application/Behaviours` 新增权限行为。行为从 `typeof(TRequest)` 读取 `PermissionAttribute`；未标记该特性的请求直接调用下一个行为。

请求类型与权限码的反射结果必须使用线程安全缓存保存，键为请求类型，值为权限码或“无权限特性”标记。缓存只承载静态类型元数据，不缓存用户、角色或权限查询结果，确保角色权限变更立即生效。

标记了特性的请求按以下步骤执行：

1. 从 `ICurrentUserService` 取得当前用户 ID。
2. 确认用户存在且未删除。
3. 基于当前单角色模型的 `SystemUser.RoleId` 查询有效角色权限。
4. 校验是否存在与 `PermissionCode` 相同的权限。
5. 未登录或用户无效时抛出项目统一的未认证异常；已登录但无权限时抛出 `BusinessException`，状态码为 `403`。
6. 校验通过后调用下一个 Pipeline 行为或 Handler。

为准确区分 `401` 与 `403`，先单独校验用户存在、启用且未删除，再以该用户的 `RoleId` 关联有效的 `SystemRolePermissions` 与 `SystemPermissions`。权限行为只依赖应用层已有的 `IDbContext`、`ICurrentUserService` 和统一异常模型；不依赖 CRM 实体、Controller 路由或具体业务模块。

### 5.3 Pipeline 顺序

在现有 MediatR 注册中固定以下执行顺序：

```text
PermissionBehaviour
    -> ValidationBehaviour
        -> TransactionBehaviour
            -> Handler
```

- 权限码由请求类型静态声明，不依赖请求参数，因此权限校验应最先执行；无权限用户不应得到参数验证结果，也不应进入验证器。
- 参数格式、必填项等输入问题由验证行为在权限通过后拒绝。
- 权限行为必须注册在事务行为之前。当前 `TransactionBehaviour` 只是透传 `next()`，尚未实际开启数据库事务；本顺序为后续启用真实事务时预留固定边界，不能把当前实现描述为已开启事务。
- Handler 内仍按业务需要进行状态和数据范围校验。

## 6. 撮合机会模块迁移范围

首期只迁移人工供需撮合机会模块，以验证通用行为的边界。

| 请求类别 | 权限码 | 说明 |
| --- | --- | --- |
| 列表、详情、活动记录 | `CRM_MATCH_OPPORTUNITY_VIEW` | 浏览撮合机会及过程记录。 |
| 创建机会、追加候选、候选状态、下一步、机会状态 | `CRM_MATCH_OPPORTUNITY_MANAGE` | 创建和维护撮合过程。 |
| 候选查询 | 无 | 仅基于有效采购需求和有效供应信息返回候选，不校验撮合模块功能权限。 |

候选查询不标记 `PermissionAttribute`，因此不会进入功能权限查询。该例外是明确的产品规则，不通过在行为中增加模块白名单或特殊分支实现。

完成撮合模块的全部请求迁移后：

- 删除 `CrmMatchOpportunityAuthorization`。
- 删除 Handler 中对 `EnsureViewAsync`、`EnsureManageAsync` 的调用。
- 不改变任何撮合业务状态与生命周期校验的位置。

后续主体、基地、厂商、采购需求等模块按同一模式逐步迁移；每次迁移只处理功能权限重复代码，不借机改动既有业务流程。

## 7. 错误与安全规则

- 未携带有效身份或用户不存在、已删除：返回未认证结果（`401`）。
- 用户有效但不拥有请求声明的权限：返回禁止访问结果（`403`）。
- 没有标记 `PermissionAttribute` 的请求不访问角色权限表，不因权限行为被拒绝。
- 资源不存在、非本人可见、状态不可变更、关联对象不可删除等业务失败，仍由 Handler 或领域规则使用既有业务异常返回。
- 前端按钮隐藏仅改善体验，后端 Query/Command 的权限行为仍是最终功能权限边界。

## 8. 测试与验收

### 8.1 自动化测试

至少覆盖：

1. 未登录请求需要权限的 Query/Command，返回 `401`。
2. 当前用户不存在或已删除，返回 `401`。
3. 已登录但无权限，返回 `403`。
4. 已拥有权限，正常进入 Handler。
5. 未标记 `PermissionAttribute` 的候选查询不读取权限关系，正常执行其业务基础条件校验。
6. 权限行为先于验证行为和事务行为执行；当前事务行为即使仍为透传实现，注册顺序也必须保持。
7. 撮合状态规则仍由原 Handler/领域测试覆盖：需求关闭、需求删除、删除被引用明细等规则不因迁移而改变。

测试源和调试产物按工作区规则分别放在 `ui-tests` 或 `agent-temp`，不混入业务源码目录。

### 8.2 验收标准

- 撮合机会模块的 Handler 不再手工查询 `SystemRolePermissions`，也不再引用 `CrmMatchOpportunityAuthorization`。
- 所有需要撮合查看或管理权限的 Query、Command 显式标记对应权限特性。
- 候选查询不校验撮合机会权限，且仍受其自身有效需求、有效供应条件约束。
- 不新增“路由 -> 权限码”的普通中间件映射。
- 权限组件不包含采购需求、撮合机会、候选或其他 CRM 业务状态判断。
- 既有撮合生命周期校验与回归测试继续通过。

## 9. 非目标

本方案不包含：

- 多权限组合、动态权限表达式或资源级 ACL。
- 通过功能权限行为实现数据范围过滤。
- 将状态机、生命周期、关联引用保护放入 Pipeline Behavior。
- 替换现有 JWT 认证机制或重构 Controller 路由。
- 一次性迁移全部业务模块。

这些能力需在出现明确业务需求后，分别设计和实施。
