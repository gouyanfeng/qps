# 采购需求标准化设计方案

**日期：** 2026-09-01  
**状态：** 已实施，历史设计

## 1. 背景与目标

当前厂商采购计划主要承接网页抓取和外部线索，保存原始标题、时间、网页地址和品类信息。它不能表达已核实的采购数量、规格、质量、价格和交期，也不能直接进入后续撮合流程。

本方案将现有采购计划直接演进为结构化采购需求。采购计划已具备厂商、时间、网页地址和品类来源，真正缺失的是需求状态与逐品类的数量、规格、质量、价格和交期。业务人员可维护外部来源或人工录入的采购需求，作为后续供需匹配、撮合机会、报价和成交的需求侧业务起点。

本阶段不建设基地供应信息、自动匹配、撮合机会、报价、样品或成交管理。

## 2. 核心关系

```text
厂商 1..N 采购需求
采购需求 1..N 采购需求明细
```

- 一个厂商可在不同时间拥有多张采购需求，历史需求相互独立，不覆盖。
- 现有采购计划即采购需求业务单据；外部抓取记录为“外部来源”，电话、拜访等新增记录为“人工录入”。
- 既有原始标题、网页地址和备注继续保留，作为来源追溯信息；人工维护的结构化字段是后续业务事实来源。
- 不存在“转为需求”操作、来源采购计划关联及一对一转换约束。

## 3. 数据模型

### 3.1 采购需求

将现有采购计划数据迁移至 `CrmPurchaseDemand`，数据库表名、实体和接口统一使用“采购需求”语义：

| 字段 | 说明 |
| --- | --- |
| `Id` | 主键 |
| `DemandNo` | 系统生成的采购需求编号 |
| `VendorId` | 所属厂商，必填 |
| `ContactId` | 需求联系人，可空，必须属于所属厂商且有效 |
| `Status` | 待确认、有效、匹配中、已完成、已关闭 |
| `DemandName` | 需求名称；外部来源时保存原始标题 |
| `DemandAt` | 需求提出时间 |
| `SourceType` | 来源类型：外部来源、人工录入 |
| `ExpectedDeliveryAt` | 期望到货日期，可空 |
| `ReceivingAddress` | 收货地，可空 |
| `Remark` | 总体备注 |
| `ClosedReason` | 关闭原因；关闭时必填 |
| `SourceUrl` | 来源页面，可空 |

采购需求不重复存储独立跟进人。它始终跟随所属厂商的当前跟进人：创建时、列表查询和厂商流转后均以 `CrmVendor.OwnerUserId` 为唯一事实来源，避免形成第二套流转状态和历史。

### 3.2 采购需求明细

新增 `CrmPurchaseDemandItem`：

| 字段 | 说明 |
| --- | --- |
| `Id` | 主键 |
| `PurchaseDemandId` | 所属采购需求 |
| `ProductName` | 采购品类，必填；从中药材品类字典选择，保存中文名称 |
| `Quantity` | 需求数量；待确认阶段可空，转为有效时必填 |
| `QuantityUnit` | 数量单位；待确认阶段可空，转为有效时必填 |
| `Specification` | 规格要求，可空 |
| `QualityRequirement` | 质量要求，可空 |
| `TargetPrice` | 目标价格，可空 |
| `PriceUnit` | 价格单位，可空，例如元/公斤 |
| `ExpectedDeliveryAt` | 明细交期，可空；优先级高于需求单交期 |
| `Remark` | 明细备注 |
| `SortOrder` | 展示顺序 |

数量单位新增为系统数据字典根节点，由需求明细选择。首批单位为“吨、公斤、克、件、批”。

## 4. 状态流转与校验

```text
待确认 -> 有效 -> 匹配中 -> 已完成
   |        |       |
   └------> 已关闭 <┘
```

- 外部导入与人工新建的需求，初始状态均为“待确认”。
- “待确认”允许暂缺数量、单位、交期等尚未核实信息。
- 转为“有效”时，至少有一条需求明细，且每条明细必须具备品类、数量和数量单位。
- 建立首个撮合机会后，在后续撮合阶段自动或手动标记为“匹配中”。本阶段先提供手动状态变更。
- “匹配中”可退回“有效”，用于无合适候选时继续等待供给。
- “已关闭”必须填写关闭原因；“已完成”和“已关闭”不可编辑或重新打开。再次发生采购时新建需求单。

## 5. 创建与历史数据

### 5.1 人工新建

1. 先选择厂商。
2. 默认带入厂商主联系人，可改选该厂商其他有效联系人。
3. `DemandAt` 默认当前时间，允许调整；`SourceType` 固定为“人工录入”。
4. 人工录入一条或多条采购需求明细。

### 5.2 外部来源与历史采购计划

1. 外部导入保留原始标题、来源页面、时间和备注，`SourceType` 标记为“外部来源”。
2. 历史采购计划统一视为“待确认”，不自动转为“有效”。
3. 历史采购计划中的品类属性转换为采购需求明细，并将属性实体类型从 `CRM_VENDOR_PURCHASE_PLAN` 改为 `CRM_PURCHASE_DEMAND`；未识别的数量、规格、价格和交期保持为空，待业务人员确认。

## 6. 页面设计

### 6.1 厂商详情页

- 将“采购计划”标签页改名为“采购需求”，按需求提出时间倒序展示该厂商的全部需求历史。
- 新增“新增采购需求”入口，支持人工录入。

### 6.2 采购需求工作台

在 CRM 下新增“采购需求”菜单，沿用既有 `QueryPage + el-table` 页面模式，不修改通用表格组件。

筛选条件：

- 需求状态
- 厂商
- 当前厂商跟进人
- 采购品类
- 需求提出时间
- 期望到货日期

列表字段：

- 采购需求编号
- 厂商
- 品类、数量摘要
- 需求提出时间、期望到货日期
- 状态
- 跟进人
- 来源类型
- 更新时间

操作：查看、编辑、确认有效、开始匹配、关闭。后续撮合阶段再增加“创建撮合机会”。

## 7. 权限

新增权限：

| 权限码 | 名称 | 用途 |
| --- | --- | --- |
| `CRM_PURCHASE_DEMAND_VIEW` | 查看采购需求 | 采购需求菜单及查询 |
| `CRM_PURCHASE_DEMAND_MANAGE` | 维护采购需求 | 新增、编辑、状态变更和关闭 |

系统管理员默认拥有两个权限。采购需求没有独立流转入口，当前跟进人随厂商流转结果变化。

## 8. 数据迁移与兼容

- 新建 `CrmPurchaseDemands`、`CrmPurchaseDemandItems` 表及数量单位字典结构；移除旧采购计划表及相关实体、接口。
- 将历史采购计划迁移为待确认采购需求：标题映射到 `DemandName`、时间映射到 `DemandAt`、页面地址映射到 `SourceUrl`、备注原样保留。
- 将历史计划品类属性迁移为采购需求明细，并将 `CrmBusinessEntityAttributes.EntityType` 更新为 `CRM_PURCHASE_DEMAND`；属性表保留为采购品类兼容投影，新增或编辑需求时与需求明细的品类集合在同一事务内同步。
- 同步将前端路由、接口路径、权限名称和页面文案统一为“采购需求”，不保留采购计划兼容入口。

## 9. 验收标准

1. 一个厂商可保存不同时间的多张采购需求，需求历史互不覆盖；外部来源和人工录入均可创建。
2. 一张需求单可保存多条品类明细，品类只能选启用的中药材品类。
3. 待确认需求可保存不完整信息；转为有效时必须补齐品类、数量和单位。
4. 联系人仅可选择所属厂商的有效联系人。
5. 厂商流转后，采购需求工作台展示的跟进人同步为厂商当前跟进人。
6. 已完成、已关闭需求不可编辑；关闭需求必须填写原因。
7. 历史采购计划显示为待确认采购需求，原始来源信息可追溯。
8. 采购需求工作台可按状态、厂商、跟进人、品类和日期筛选。
9. 后端构建、迁移、单元测试和前端构建通过；关键操作完成浏览器验收。
