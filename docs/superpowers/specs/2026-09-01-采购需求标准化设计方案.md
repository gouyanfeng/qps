# 采购需求标准化设计方案

**日期：** 2026-09-01  
**状态：** 待评审

## 1. 背景与目标

当前厂商采购计划主要承接网页抓取和外部线索，保存原始标题、时间、网页地址和品类信息。它不能表达已核实的采购数量、规格、质量、价格和交期，也不能直接进入后续撮合流程。

本方案新增结构化采购需求，使业务人员可以将采购计划转化为可执行需求，或直接录入电话、拜访等渠道发现的需求。采购需求是后续供需匹配、撮合机会、报价和成交的需求侧业务起点。

本阶段不建设基地供应信息、自动匹配、撮合机会、报价、样品或成交管理。

## 2. 核心关系

```text
厂商 1..N 采购计划
厂商 1..N 采购需求单
采购计划 0..1 采购需求单
采购需求单 1..N 采购需求明细
```

- 厂商可在不同时间发起多张采购需求，历史需求相互独立，不覆盖。
- 采购计划是原始线索，采购需求是人工确认后的业务单据。
- 一条采购计划最多转换为一张采购需求单，防止同一来源重复进入业务流程。
- 采购需求可直接人工新建，来源采购计划可为空。
- 采购计划更新后不得自动覆盖已创建采购需求，避免覆盖人工核实结果。

## 3. 数据模型

### 3.1 采购需求单

新增 `CrmPurchaseDemand`：

| 字段 | 说明 |
| --- | --- |
| `Id` | 主键 |
| `DemandNo` | 系统生成的需求编号 |
| `VendorId` | 所属厂商，必填 |
| `SourcePurchasePlanId` | 来源采购计划，可空；非空时唯一 |
| `ContactId` | 需求联系人，可空，必须属于所属厂商且有效 |
| `Status` | 待确认、有效、匹配中、已完成、已关闭 |
| `DemandAt` | 需求提出时间，必填 |
| `ExpectedDeliveryAt` | 期望到货日期，可空 |
| `ReceivingAddress` | 收货地，可空 |
| `Remark` | 总体备注 |
| `ClosedReason` | 关闭原因；关闭时必填 |

采购需求不重复存储独立跟进人。它始终跟随所属厂商的当前跟进人：创建时、列表查询和厂商流转后均以 `CrmVendor.OwnerUserId` 为唯一事实来源，避免形成第二套流转状态和历史。

### 3.2 采购需求明细

新增 `CrmPurchaseDemandItem`：

| 字段 | 说明 |
| --- | --- |
| `Id` | 主键 |
| `PurchaseDemandId` | 所属采购需求单 |
| `ProductName` | 采购品类，必填；从中药材品类字典选择，保存中文名称 |
| `Quantity` | 需求数量；待确认阶段可空，转为有效时必填 |
| `QuantityUnit` | 数量单位；待确认阶段可空，转为有效时必填 |
| `Specification` | 规格要求，可空 |
| `QualityRequirement` | 质量要求，可空 |
| `TargetPrice` | 目标价格，可空 |
| `PriceUnit` | 价格单位，可空，例如元/公斤 |
| `ExpectedDeliveryAt` | 明细交期，可空；优先级高于需求单交期 |
| `Remark` | 明细备注 |
| `SortOrder` | 展示顺序 |

数量单位新增为系统数据字典根节点，由需求明细选择。首批单位为“吨、公斤、克、件、批”。

## 4. 状态流转与校验

```text
待确认 -> 有效 -> 匹配中 -> 已完成
   |        |       |
   └------> 已关闭 <┘
```

- 新建需求及从采购计划转换的需求，初始状态均为“待确认”。
- “待确认”允许暂缺数量、单位、交期等尚未核实信息。
- 转为“有效”时，至少有一条需求明细，且每条明细必须具备品类、数量和数量单位。
- 建立首个撮合机会后，在后续撮合阶段自动或手动标记为“匹配中”。本阶段先提供手动状态变更。
- “匹配中”可退回“有效”，用于无合适候选时继续等待供给。
- “已关闭”必须填写关闭原因；“已完成”和“已关闭”不可编辑或重新打开。再次发生采购时新建需求单。

## 5. 创建与来源转换

### 5.1 从采购计划转换

1. 校验来源计划尚未关联采购需求。
2. 创建一张“待确认”采购需求单。
3. `VendorId` 固定为来源计划所属厂商。
4. `DemandAt` 默认取采购计划时间；为空时取当前时间。
5. 联系人默认选择厂商主联系人，可在保存前改选其他有效联系人。
6. 采购计划中的品类复制为采购需求明细；未识别数量、规格和交期由业务人员补充。

### 5.2 人工新建

1. 先选择厂商。
2. 默认带入厂商主联系人，可改选该厂商其他有效联系人。
3. `DemandAt` 默认当前时间，允许调整。
4. 人工录入一条或多条采购需求明细。

## 6. 页面设计

### 6.1 厂商详情页

- 保留“采购计划”标签页，作为原始线索列表。
- 采购计划行增加“转为需求”操作；已转换时显示关联需求编号和状态，并隐藏转换入口。
- 新增“采购需求”标签页，按需求提出时间倒序展示该厂商的全部需求历史。
- 新增“新增采购需求”入口，支持人工录入。

### 6.2 采购需求工作台

在 CRM 下新增“采购需求”菜单，沿用既有 `QueryPage + el-table` 页面模式，不修改通用表格组件。

筛选条件：

- 需求状态
- 厂商
- 当前厂商跟进人
- 采购品类
- 需求提出时间
- 期望到货日期

列表字段：

- 需求编号
- 厂商
- 品类、数量摘要
- 需求提出时间、期望到货日期
- 状态
- 跟进人
- 来源类型和来源采购计划
- 更新时间

操作：查看、编辑、确认有效、开始匹配、关闭。后续撮合阶段再增加“创建撮合机会”。

## 7. 权限

新增权限：

| 权限码 | 名称 | 用途 |
| --- | --- | --- |
| `CRM_PURCHASE_DEMAND_VIEW` | 查看采购需求 | 采购需求菜单及查询 |
| `CRM_PURCHASE_DEMAND_MANAGE` | 维护采购需求 | 新增、编辑、转换、状态变更和关闭 |

系统管理员默认拥有两个权限。采购需求没有独立流转入口，当前跟进人随厂商流转结果变化。

## 8. 数据迁移与兼容

- 新增采购需求单、采购需求明细和数量单位字典结构。
- 不将历史采购计划批量自动转换为采购需求，避免将未核实、过期线索误判为有效需求。
- 保留现有采购计划表、接口和页面行为，不改变其作为来源线索的职责。
- 新增来源计划唯一约束：同一非空 `SourcePurchasePlanId` 只允许一张采购需求单。

## 9. 验收标准

1. 一个厂商可保存不同时间的多张采购需求，需求历史互不覆盖。
2. 一张需求单可保存多条品类明细，品类只能选启用的中药材品类。
3. 同一采购计划不可重复转换为需求。
4. 待确认需求可保存不完整信息；转为有效时必须补齐品类、数量和单位。
5. 联系人仅可选择所属厂商的有效联系人。
6. 厂商流转后，采购需求工作台展示的跟进人同步为厂商当前跟进人。
7. 已完成、已关闭需求不可编辑；关闭需求必须填写原因。
8. 厂商详情页可查看来源计划与采购需求的关联关系。
9. 采购需求工作台可按状态、厂商、跟进人、品类和日期筛选。
10. 后端构建、迁移、单元测试和前端构建通过；关键操作完成浏览器验收。
