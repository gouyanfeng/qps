# 人工供需撮合机会设计方案

**日期：** 2026-09-05  
**状态：** 已确认设计，待实施

## 1. 目标与边界

在现有采购需求和基地供应信息之上，提供首版人工撮合台。采购需求承载厂商、联系人、交期、收货地和多条采购明细等共同事实；业务人员以一条有效采购明细为单位建立一轮撮合机会，并持续记录候选判断和下一步动作。

本期只建设人工候选筛选和撮合推进，不建设自动匹配评分、报价、样品、验收、合同、订单、成交金额、库存扣减或复购识别。

现有 `CrmFollowRecord` 继续承载基地主体、厂商的客户沟通；现有 `CrmTransferRecord` 继续承载主体、厂商的归属流转。本期撮合过程不复用这两张表。

## 2. 业务流程

```text
有效采购需求
    -> 在弹窗中选择采购明细
    -> 判断该明细是否已有未关闭机会
    -> 无机会时发起撮合，已有机会时查看或追加候选
    -> 人工筛选有效供应信息
    -> 选中多个候选并创建一轮撮合机会
    -> 评估候选、维护下一步动作
    -> 暂停、恢复或关闭本轮机会
```

一条采购需求明细可创建多轮撮合机会，但同一时刻至多存在一条未关闭机会。某一轮关闭后，只要所属采购需求仍为“有效”，即可重新发起下一轮，不覆盖历史。

采购需求状态只表达需求是否已确认可用，不再表达撮合进度。创建机会时不再把所属采购需求改为“匹配中”；明细的撮合状态由其最新机会记录派生，避免同一采购需求中的其他明细被错误锁定。

采购需求自身展示聚合后的“撮合进度”，但不保存为字段：`已发起数 / 明细总数`，以及“待撮合、撮合中、已暂停、已结束”的明细数量。该进度用于跨厂商扫描，点击后进入采购明细选择弹窗查看具体状态和操作。

## 3. 数据模型

### 3.1 `CrmMatchOpportunities`

一行代表围绕一条采购需求明细开展的一轮撮合过程。

| 字段 | 说明 |
| --- | --- |
| `DemandItemId` | 来源采购需求明细，必填。 |
| `DemandId`、`VendorId` | 冗余关联，仅用于列表筛选和展示。 |
| `DemandProductName` | 采购品类快照。 |
| `DemandQuantity`、`QuantityUnit` | 采购数量快照。 |
| `Specification`、`QualityRequirement` | 采购规格、质量要求快照。 |
| `ExpectedDeliveryAt`、`DeliveryAddress` | 采购交期、收货地快照。 |
| `OwnerUserId` | 撮合跟进人，创建时取厂商跟进人。 |
| `Status` | `推进中`、`暂停`、`已关闭`。 |
| `NextAction`、`NextActionAt` | 当前下一步动作及计划时间。 |
| `ClosedReason` | 状态为“已关闭”时必填。 |

实体继承项目现有 `BaseEntity`，复用审计字段。

数据库以 `DemandItemId` 建立仅覆盖“推进中、暂停”且未删除记录的唯一筛选索引，从存储层保证同一采购明细不能并发创建两条未关闭机会。

### 3.2 `CrmMatchCandidates`

一行代表某轮撮合中实际纳入比较的一条基地供应信息。

| 字段 | 说明 |
| --- | --- |
| `MatchOpportunityId` | 所属撮合机会，必填。 |
| `HerbBaseSupplyId` | 来源基地供应信息，必填。 |
| `HerbBaseId`、`HerbBaseSubjectId` | 冗余关联，仅用于筛选与展示。 |
| `SubjectName`、`HerbBaseName` | 基地主体、基地名称快照。 |
| `ProductName` | 供应品类快照。 |
| `AvailableQuantity`、`QuantityUnit` | 可供量快照。 |
| `Specification`、`QualityRequirement` | 供应规格、质量条件快照。 |
| `ExpectedPrice`、`PriceUnit` | 供应预期价格快照。 |
| `SupplyCycle`、`ValidUntil` | 供货周期、有效期快照。 |
| `Status` | `待评估`、`保留`、`淘汰`。 |
| `EliminationReason` | 状态为“淘汰”时必填。 |
| `SortOrder` | 候选展示顺序。 |

同一撮合机会不得重复关联同一条供应信息。候选不提供物理删除；不再推进时改为“淘汰”，保留判断原因。

### 3.3 `CrmBusinessActivities`

这是最小的通用业务过程记录表，首期只用于 `MATCH_OPPORTUNITY`，后续实际出现其他流程需求时再复用。

| 字段 | 说明 |
| --- | --- |
| `EntityType` | 业务对象类型，首期固定为 `MATCH_OPPORTUNITY`。 |
| `EntityId` | 业务对象 ID，首期为撮合机会 ID。 |
| `ActionType` | `创建机会`、`加入候选`、`保留候选`、`淘汰候选`、`更新下一步`、`暂停`、`恢复`、`关闭`。 |
| `Content` | 不可变的时间线说明，保留动作发生时的名称、条件或原因。 |

该表不增加 `OperatorUserId`、`RelatedEntityType`、`RelatedEntityId` 或 JSON 扩展字段。操作人和操作时间直接复用 `BaseEntity.CreatedBy`、`BaseEntity.CreatedAt`；当前 P0 没有消费关联子对象的交互，不为假设场景提前建字段。

## 4. 快照规则

机会和候选均保留本轮判断所依据的最小条件快照。采购需求、供应信息随后被修改时，历史撮合不应被最新数据改写。

- 保留 `DemandItemId`、`HerbBaseSupplyId`，可跳转查看当前档案。
- 详情明确区分“撮合时条件”和“当前档案”。
- 不复制无关档案字段，也不复制完整基地或厂商资料。

## 5. 候选筛选规则

候选查询默认带入采购明细品类，但品类是可清空、可改选的字典筛选项，不是硬约束。系统不做自动推荐、自动评分或自动排序；可供量不足的供应信息可以展示，由业务人员判断是否多基地组合供给。

供应状态为“有效”且 `ValidUntil` 不早于服务端当前北京时间日期仍是候选基础条件。地区、品类、可供量、规格、质量条件、供货周期和预期价格均为业务人员可调整的筛选项；创建和追加候选时再次校验供应基础条件，但不强制供应品类等于采购品类。

## 6. 状态规则与过程记录

| 操作 | 校验与结果 |
| --- | --- |
| 创建机会 | 所属采购需求必须为“有效”，该采购明细不存在“推进中”或“暂停”机会，且至少选择一条符合候选基础条件的供应信息；机会创建为“推进中”，候选创建为“待评估”。 |
| 追加候选 | 仅“推进中”机会可操作；选择供应须符合候选基础条件且未在该机会中出现。 |
| 保留候选 | 仅“推进中”机会可操作，将候选改为“保留”。 |
| 淘汰候选 | 仅“推进中”机会可操作，淘汰原因必填。 |
| 更新下一步 | 仅“推进中”或“暂停”机会可操作，更新动作或计划时间并写过程记录。 |
| 暂停/恢复 | 仅允许“推进中 -> 暂停 -> 推进中”。 |
| 关闭 | 关闭原因必填，关闭后机会和候选不可再编辑。 |
| 重新撮合 | 最近机会为“已关闭”且所属采购需求仍为“有效”时允许；创建新机会，不恢复或覆盖旧机会。 |

每次上述操作在同一事务内更新业务数据并写入一条 `CrmBusinessActivities`。时间线将审计字段 `CreatedBy` 解析为用户 ID，关联 `SystemUsers` 展示操作人姓名。

## 7. 页面与接口

### 7.1 入口和候选筛选

采购需求菜单保留为跨厂商查询入口，厂商详情保留为单厂商维护入口；二者均在“选择采购明细”弹窗中展示每条明细的撮合状态和对应操作。

- 采购需求列表和厂商详情采购需求表都展示同一“撮合进度”：`已发起 2/3 · 1 撮合中 · 1 已结束`；数字由明细最新机会实时聚合，点击进度打开采购明细选择弹窗。
- 每行使用单选按钮明确选择采购明细，点击整行同步选中；未选择时“继续”禁用，即使只有一条明细也保留该确认步骤。
- 从未创建机会的明细显示“开始撮合”；最近机会已关闭时显示“重新撮合”和“查看历史”；已有“推进中”或“暂停”机会时显示“查看撮合”。
- 候选筛选页展示需求快照，品类筛选默认使用采购品类但允许修改；候选表必须展示供应品类。
- 创建成功后打开新机会详情。详情提供“追加候选”，复用候选筛选页的筛选能力，提交到当前机会并自动排除已加入候选。

### 7.2 撮合机会工作台

CRM 新增“撮合机会”菜单，沿用 `QueryPage + el-table + 详情抽屉`，不修改通用表格组件。

- 列表筛选：机会状态、品类、需求厂商、基地主体、撮合跟进人、下一步时间。
- 详情：需求条件快照、候选列表、过程时间线、下一步动作。
- 操作：添加候选、保留候选、淘汰候选、更新下一步、暂停、恢复、关闭。

P0 不把撮合机会接入现有“跟进任务”工作台；`NextActionAt` 先在撮合机会列表中筛选、排序和处理，避免扩大当前任务对象范围。

### 7.3 接口边界

接口沿用 CQRS 与明确业务路由，不向前端暴露泛化的活动实体操作：

```text
GET  /api/admin/crm/match-opportunities
GET  /api/admin/crm/match-opportunities/{id}
POST /api/admin/crm/vendor-demand-items/{demandItemId}/match-opportunities/candidates
POST /api/admin/crm/vendor-demand-items/{demandItemId}/match-opportunities
POST /api/admin/crm/match-opportunities/{id}/candidates
PATCH /api/admin/crm/match-opportunities/{id}/candidates/{candidateId}/status
PATCH /api/admin/crm/match-opportunities/{id}/next-action
PATCH /api/admin/crm/match-opportunities/{id}/status
GET  /api/admin/crm/match-opportunities/{id}/activities
```

采购需求列表及厂商详情查询的每个 `CrmVendorDemandItem` 都返回以下派生字段，不新增数据库冗余列：

| 字段 | 说明 |
| --- | --- |
| `MatchOpportunityId` | 该明细最新机会的 ID；从未创建时为空。 |
| `MatchOpportunityStatus` | 最新机会状态：`推进中`、`暂停` 或 `已关闭`；从未创建时为空。 |
| `MatchCandidateCount` | 最新机会的候选数；从未创建时为 `0`。 |
| `MatchDisplayStatus` | 基于最新机会计算的页面状态：`待撮合`、`撮合中`、`已暂停`、`已结束`。 |

每个 `CrmVendorDemand` 同时返回 `MatchProgress` 聚合 DTO：`TotalItemCount`、`StartedItemCount`、`PendingItemCount`、`InProgressItemCount`、`PausedItemCount`、`ClosedItemCount`。查询层从明细最新机会计算这些值，不新增数据表字段。

机会列表查询支持按 `DemandItemId` 精确筛选，供“查看撮合”定位当前机会。候选查询支持可选 `ProductName`；追加候选查询额外接收 `ExcludeOpportunityId`，排除该机会已关联的供应。

## 8. 权限与数据范围

新增权限：

| 权限码 | 用途 |
| --- | --- |
| `CRM_MATCH_OPPORTUNITY_VIEW` | 菜单、列表、详情和候选查询。 |
| `CRM_MATCH_OPPORTUNITY_MANAGE` | 创建机会、维护候选、更新下一步和状态。 |

本期不新建撮合机会流转能力。机会创建时取厂商跟进人为撮合跟进人；后续是否建设独立转交，需在实际出现跨人协同需求后另行设计。

## 9. 验收与测试

现有状态为“匹配中”的采购需求是旧实现写入的撮合进度，不再具有业务含义。随本次迁移统一回填为“有效”，不修改已存在的机会、候选和活动历史；回填前后需记录数量并核对未删除采购需求总数不变。

后端覆盖：仅有效采购需求可创建、同明细只允许一条未关闭机会、候选基础条件、跨品类候选创建、重复候选拒绝、追加候选自动排除、淘汰及关闭原因必填、关闭后不可编辑、关闭后新建下一轮、过程时间线完整性、权限拒绝和历史状态回填。

UI 测试在 `ui-tests` 中通过页面操作完成：创建含多条明细的有效采购需求、确认采购需求列表和厂商详情的撮合进度一致、维护不同品类的有效供应信息、在明细选择弹窗中确认状态、创建机会、追加候选、保留和淘汰候选、暂停恢复、关闭、重新撮合、刷新回查时间线和状态。测试使用隔离端口 `5174/5001`，不直接调用业务 API。
