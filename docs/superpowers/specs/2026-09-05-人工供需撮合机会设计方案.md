# 人工供需撮合机会设计方案

**日期：** 2026-09-05  
**状态：** 已实施；闭环扩展已完成验证

## 1. 目标与边界

在现有采购需求和基地供应信息之上，提供首版人工撮合台。采购需求承载厂商、联系人、交期、收货地和多条采购明细等共同事实；业务人员以一条有效采购明细为单位建立一轮撮合机会，并持续记录候选判断和下一步动作。

本期只建设人工候选筛选和撮合推进，不建设自动匹配评分、报价、样品、验收、合同、订单、成交金额、库存扣减或复购识别。

现有 `CrmFollowRecord` 继续承载基地主体、厂商的客户沟通；现有 `CrmTransferRecord` 继续承载主体、厂商的归属流转。本期撮合过程不复用这两张表。

## 2. 业务流程

```text
有效采购需求
    -> 在弹窗中选择采购明细
    -> 判断该明细是否已有未关闭机会
    -> 无机会时发起撮合，已有机会时查看或追加候选
    -> 人工筛选有效供应信息
    -> 选中多个候选并创建一轮撮合机会
    -> 评估候选、保留或中选候选、维护下一步动作
    -> 暂停、恢复或关闭本轮机会
```

一条采购需求明细可创建多轮撮合机会，但同一时刻至多存在一条未关闭机会。某一轮关闭后，只要所属采购需求仍为“有效”，即可重新发起下一轮，不覆盖历史。

采购需求状态只表达需求是否已确认可用，不再表达撮合进度。创建机会时不再把所属采购需求改为“匹配中”；明细的撮合状态由其最新机会记录派生，避免同一采购需求中的其他明细被错误锁定。

采购需求菜单展示聚合后的“撮合进度”，但不保存为字段：`已发起数 / 明细总数`，以及“待撮合、撮合中、已暂停、已结束”的明细数量。该进度用于跨厂商扫描，点击后进入采购明细选择弹窗查看具体状态和操作。厂商详情不展示撮合进度，也不承担撮合操作。

## 3. 数据模型

### 3.1 `CrmMatchOpportunities`

一行代表围绕一条采购需求明细开展的一轮撮合过程。

| 字段 | 说明 |
| --- | --- |
| `DemandItemId` | 来源采购需求明细，必填。 |
| `DemandId`、`VendorId` | 冗余关联，仅用于列表筛选和展示。 |
| `DemandProductName` | 采购品类快照。 |
| `DemandQuantity`、`QuantityUnit` | 采购数量快照。 |
| `Specification`、`QualityRequirement` | 采购规格、质量要求快照。 |
| `ExpectedDeliveryAt`、`DeliveryAddress` | 采购交期、收货地快照。 |
| `OwnerUserId` | 撮合跟进人，创建时取厂商跟进人。 |
| `Status` | `推进中`、`暂停`、`已关闭`。 |
| `NextAction`、`NextActionAt` | 当前下一步动作及计划时间。 |
| `CloseResult` | 关闭结果：`撮合成功`、`未成交`、`需求取消`。仅关闭时有值。 |
| `ClosedReason` | 关闭结果为`未成交`或`需求取消`时必填。 |

实体继承项目现有 `BaseEntity`，复用审计字段。

数据库以 `DemandItemId` 建立仅覆盖“推进中、暂停”且未删除记录的唯一筛选索引，从存储层保证同一采购明细不能并发创建两条未关闭机会。

### 3.2 `CrmMatchCandidates`

一行代表某轮撮合中实际纳入比较的一条基地供应信息。

| 字段 | 说明 |
| --- | --- |
| `MatchOpportunityId` | 所属撮合机会，必填。 |
| `HerbBaseSupplyId` | 来源基地供应信息，必填。 |
| `HerbBaseId`、`HerbBaseSubjectId` | 冗余关联，仅用于筛选与展示。 |
| `SubjectName`、`HerbBaseName` | 基地主体、基地名称快照。 |
| `ProductName` | 供应品类快照。 |
| `AvailableQuantity`、`QuantityUnit` | 可供量快照。 |
| `Specification`、`QualityRequirement` | 供应规格、质量条件快照。 |
| `ExpectedPrice`、`PriceUnit` | 供应预期价格快照。 |
| `SupplyCycle`、`ValidUntil` | 供货周期、有效期快照。 |
| `Status` | `待评估`、`保留`、`中选`、`淘汰`。 |
| `EliminationReason` | 状态为“淘汰”时必填。 |
| `SortOrder` | 候选展示顺序。 |

同一撮合机会不得重复关联同一条供应信息。候选不提供物理删除；不再推进时改为“淘汰”，保留判断原因。`中选`表示本轮撮合最终选择的供应方，可同时存在多条；本期不记录每家承担数量，不代表订单或履约完成。

### 3.3 `CrmBusinessActivities`

这是最小的通用业务过程记录表，首期只用于 `MATCH_OPPORTUNITY`，后续实际出现其他流程需求时再复用。

| 字段 | 说明 |
| --- | --- |
| `EntityType` | 业务对象类型，首期固定为 `MATCH_OPPORTUNITY`。 |
| `EntityId` | 业务对象 ID，首期为撮合机会 ID。 |
| `ActionType` | `创建机会`、`加入候选`、`保留候选`、`中选候选`、`淘汰候选`、`更新下一步`、`暂停`、`恢复`、`关闭`。 |
| `Content` | 不可变的时间线说明，保留动作发生时的名称、条件或原因。 |

该表不增加 `OperatorUserId`、`RelatedEntityType`、`RelatedEntityId` 或 JSON 扩展字段。操作人和操作时间直接复用 `BaseEntity.CreatedBy`、`BaseEntity.CreatedAt`；当前 P0 没有消费关联子对象的交互，不为假设场景提前建字段。

## 4. 快照规则

机会和候选均保留本轮判断所依据的最小条件快照。采购需求、供应信息随后被修改时，历史撮合不应被最新数据改写。

- 保留 `DemandItemId`、`HerbBaseSupplyId`，可跳转查看当前档案。
- 详情明确区分“撮合时条件”和“当前档案”。
- 不复制无关档案字段，也不复制完整基地或厂商资料。

机会详情同时返回候选供应当前状态，不写入历史快照：

- `当前正常`：当前供应存在、状态有效、未过有效期，且关键条件与快照一致。
- `条件已变更`：当前供应仍有效，但品类、可供量、单位、规格、质量、预期价格、价格单位、供货周期或有效期与快照不同。
- `已失效`：当前供应不存在、已删除、状态无效或已过有效期。

`中选`和“撮合成功”关闭前只校验当前供应是否有效，不因“条件已变更”自动拒绝；业务人员必须在详情中基于当前值重新判断。历史快照始终保留，不自动覆盖候选状态。

## 5. 候选筛选规则

候选查询默认带入采购明细品类，但品类是可清空、可改选的字典筛选项，不是硬约束。系统不做自动推荐、自动评分或自动排序；可供量不足的供应信息可以展示，由业务人员判断是否多基地组合供给。

供应状态为“有效”且 `ValidUntil` 不早于服务端当前北京时间日期仍是候选基础条件。地区、品类、可供量、规格、质量条件、供货周期和预期价格均为业务人员可调整的筛选项；创建和追加候选时再次校验供应基础条件，但不强制供应品类等于采购品类。

## 6. 状态规则与过程记录

| 操作 | 校验与结果 |
| --- | --- |
| 创建机会 | 所属采购需求必须为“有效”，该采购明细不存在“推进中”或“暂停”机会，且至少选择一条符合候选基础条件的供应信息；下一步和计划时间必填；机会创建为“推进中”，候选创建为“待评估”。 |
| 追加候选 | 仅“推进中”机会可操作；选择供应须符合候选基础条件且未在该机会中出现。 |
| 保留候选 | 仅“推进中”机会可操作，将候选改为“保留”；用于撤销“中选”或恢复被误淘汰的候选。 |
| 中选候选 | 仅“推进中”机会可操作；供应当前必须有效；将候选改为“中选”。 |
| 淘汰候选 | 仅“推进中”机会可操作，淘汰原因必填。 |
| 更新下一步 | 仅“推进中”或“暂停”机会可操作；下一步动作和计划时间必须同时填写，并写过程记录。 |
| 暂停/恢复 | 仅允许“推进中 -> 暂停 -> 推进中”；恢复时，原计划时间早于服务端当前北京时间则必须重新填写下一步和计划时间。 |
| 关闭 | 必须选择关闭结果。`撮合成功`必须至少有一条当前有效的中选候选；`未成交`、`需求取消`必须填写关闭原因且不得保留中选候选；关闭后机会和候选不可再编辑。 |
| 重新撮合 | 最近机会为“已关闭”且所属采购需求仍为“有效”时允许；创建新机会，不恢复或覆盖旧机会。 |

每次上述操作在同一事务内更新业务数据并写入一条 `CrmBusinessActivities`。关闭活动必须记录关闭结果和关闭原因；时间线将审计字段 `CreatedBy` 解析为用户 ID，关联 `SystemUsers` 展示操作人姓名。

采购需求存在“推进中”或“暂停”撮合机会时，不允许改为“已完成”、关闭或删除该采购需求，必须先关闭全部未关闭机会。已被任一撮合机会引用的采购明细不允许从采购需求中删除，避免历史机会失去来源明细。

采购需求存在未关闭机会时，不允许修改影响撮合判断的字段：采购明细的品类、数量、单位、规格、质量、目标价、价格单位、交期，以及需求收货地。需求名称、联系人、来源和备注仍可维护，避免无关资料维护被阻断。

## 7. 页面与接口

### 7.1 入口和候选筛选

厂商详情与采购需求菜单职责分开：厂商详情是单厂商资料维护入口；采购需求菜单是跨厂商查询、撮合和查看进度的唯一入口。

- 厂商详情的采购需求区域仅维护采购需求事实数据，包括新增、编辑、确认有效和关闭；不展示“开始撮合”、撮合进度、明细撮合状态或进入撮合机会的入口。
- 采购需求列表展示“撮合进度”：`已发起 2/3 · 1 撮合中 · 1 已结束`；数字由明细最新机会实时聚合，点击进度打开采购明细选择弹窗。
- 采购需求列表不提供编辑入口。采购需求的新增、编辑、确认有效和关闭均在厂商详情内完成，避免在跨厂商撮合页面混入资料维护。
- 每行使用单选按钮明确选择采购明细，点击整行同步选中；未选择时“继续”禁用，即使只有一条明细也保留该确认步骤。
- 从未创建机会的明细显示“开始撮合”；最近机会已关闭时显示“重新撮合”和“查看历史”；已有“推进中”或“暂停”机会时显示“查看撮合”。
- 候选筛选页展示需求快照，品类筛选默认使用采购品类但允许修改；候选表必须展示供应品类。
- 候选查询不校验撮合机会权限码，仅按有效采购需求和有效供应信息返回候选；创建机会、追加候选及后续维护操作仍校验撮合管理权限。
- 创建成功后打开新机会详情。详情提供“追加候选”，复用候选筛选页的筛选能力，提交到当前机会并自动排除已加入候选。
- 候选列表增加“当前状态”列。`条件已变更`展示当前值与快照差异；`已失效`禁止中选和成功关闭，但不删除历史候选。
- 创建机会弹窗在提交候选前填写下一步和计划时间；缺任一项不能创建。
- 机会详情增加“中选”操作。存在中选候选时，非成功关闭不可提交；成功关闭时展示中选候选数量和关闭结果。
- 已关闭明细在采购明细选择弹窗提供“查看历史”入口，按 `DemandItemId` 打开该明细全部历史机会；“重新撮合”仍单独创建新机会。
- 撮合机会页由主布局缓存。无论页面是首次进入还是从缓存重新激活，只要路由携带 `demandId`，均须重新查询该采购需求、重置上一次选择的明细和候选筛选状态，并打开“选择采购明细”弹窗；不能只依赖路由参数变化监听。同一 `demandId` 再次点击“开始撮合”时，仍必须可见该弹窗。路由不携带 `demandId` 时，须关闭该弹窗并清理入口临时状态，避免旧需求残留。

### 7.2 撮合机会工作台

CRM 新增“撮合机会”菜单，沿用 `QueryPage + el-table + 详情抽屉`，不修改通用表格组件。

- 列表筛选：机会状态、品类、需求厂商、基地主体、撮合跟进人、下一步时间。
- 详情：需求条件快照、候选列表、过程时间线、下一步动作。
- 操作：添加候选、保留候选、中选候选、淘汰候选、更新下一步、暂停、恢复、关闭。

P0 不把撮合机会接入现有“跟进任务”工作台；`NextActionAt` 先在撮合机会列表中筛选、排序和处理，避免扩大当前任务对象范围。

### 7.3 接口边界

接口沿用 CQRS 与明确业务路由，不向前端暴露泛化的活动实体操作：

```text
GET  /api/admin/crm/match-opportunities
GET  /api/admin/crm/match-opportunities/{id}
POST /api/admin/crm/vendor-demand-items/{demandItemId}/match-opportunities/candidates
POST /api/admin/crm/vendor-demand-items/{demandItemId}/match-opportunities
POST /api/admin/crm/match-opportunities/{id}/candidates
PATCH /api/admin/crm/match-opportunities/{id}/candidates/{candidateId}/status
PATCH /api/admin/crm/match-opportunities/{id}/next-action
PATCH /api/admin/crm/match-opportunities/{id}/status
GET  /api/admin/crm/match-opportunities/{id}/activities
```

本轮接口字段契约如下。路由中的 ID 由控制器写入命令对象，前端不重复在请求体中传递；状态、关闭结果和候选状态均使用中文枚举值，与页面显示保持一致。

| 请求 | 必填字段 | 规则 |
| --- | --- | --- |
| `CreateCrmMatchOpportunityCommand` | `SupplyIds`、`NextAction`、`NextActionAt` | 创建机会时必须同时提交候选和下一步安排。 |
| `AddCrmMatchOpportunityCandidatesCommand` | `SupplyIds` | 仅追加未加入当前机会且当前有效的供应。 |
| `UpdateCrmMatchCandidateStatusCommand` | `Status` | 支持`保留`、`中选`、`淘汰`；`淘汰`时 `EliminationReason` 必填，`中选`前重新校验当前供应有效性。 |
| `UpdateCrmMatchOpportunityNextActionCommand` | `NextAction`、`NextActionAt` | 两项必须同时填写；暂停中的机会也可更新安排。 |
| `UpdateCrmMatchOpportunityStatusCommand` | `Status` | 关闭时同时提交 `CloseResult`，非成功关闭提交 `ClosedReason`；恢复且原计划时间早于服务端当前北京时间时，同时提交新的 `NextAction`、`NextActionAt`。 |

机会列表、详情 DTO 都返回 `CloseResult`；详情中的候选 DTO 除快照字段外，还返回当前供应条件、`CurrentState` 和 `CurrentChangedFields`。当前供应条件只用于本次查询展示，不写回候选快照。

候选当前状态必须通过一次包含软删除记录的供应查询计算：查询不到供应或供应已软删除时返回`已失效`，不能因全局查询筛选器直接丢失候选。`CurrentChangedFields` 返回发生变化的中文字段名列表，范围固定为品类、可供量、数量单位、规格、质量要求、预期价格、价格单位、供货周期、有效期，供前端逐项展示差异。

采购需求列表查询的每个 `CrmVendorDemandItem` 都返回以下派生字段，不新增数据库冗余列：

| 字段 | 说明 |
| --- | --- |
| `MatchOpportunityId` | 该明细最新机会的 ID；从未创建时为空。 |
| `MatchOpportunityStatus` | 最新机会状态：`推进中`、`暂停` 或 `已关闭`；从未创建时为空。 |
| `MatchCandidateCount` | 最新机会的候选数；从未创建时为 `0`。 |
| `MatchDisplayStatus` | 基于最新机会计算的页面状态：`待撮合`、`撮合中`、`已暂停`、`已结束`。 |

机会详情的候选 DTO 增加派生字段 `CurrentState`、`CurrentChangedFields` 与当前供应条件，用于展示当前档案和撮合快照的差异；这些字段不写入 `CrmMatchCandidates`。

采购需求列表中的每个 `CrmVendorDemand` 同时返回 `MatchProgress` 聚合 DTO：`TotalItemCount`、`StartedItemCount`、`PendingItemCount`、`InProgressItemCount`、`PausedItemCount`、`ClosedItemCount`。查询层从明细最新机会计算这些值，不新增数据表字段；厂商详情不消费该 DTO。

机会列表查询支持按 `DemandItemId` 精确筛选，供“查看撮合”定位当前机会。候选查询支持可选 `ProductName`；追加候选查询额外接收 `ExcludeOpportunityId`，排除该机会已关联的供应。

### 7.4 本期边界

- 不做价格、数量或单位换算。候选列表完整展示数量单位和价格单位，由业务人员人工判断可比性。
- 多个中选候选只表示被选择的供应方集合；因本期不记录候选承担数量，系统不判断合计可供量是否完整覆盖采购数量。
- `撮合成功`仅表示本轮人工撮合已选定有效供应方，不创建订单、不锁定供应库存，也不表示后续履约完成。

## 8. 权限与数据范围

新增权限：

| 权限码 | 用途 |
| --- | --- |
| `CRM_MATCH_OPPORTUNITY_VIEW` | 菜单、列表和详情。 |
| `CRM_MATCH_OPPORTUNITY_MANAGE` | 创建机会、维护候选、更新下一步和状态。 |

本期不新建撮合机会流转能力。机会创建时取厂商跟进人为撮合跟进人；后续是否建设独立转交，需在实际出现跨人协同需求后另行设计。

## 9. 验收与测试

现有状态为“匹配中”的采购需求是旧实现写入的撮合进度，不再具有业务含义。随本次迁移统一回填为“有效”；回填前后需记录数量并核对未删除采购需求总数不变。

历史库若存在同一采购明细的多条“推进中”或“暂停”机会，迁移按“最后更新时间、创建时间、机会 ID”倒序保留最新的一条，将其余机会改为“已关闭”，关闭原因固定为“系统迁移：同一采购明细仅保留最新未关闭机会”，并为每条被关闭机会补一条“系统迁移关闭”活动。候选和原有活动历史不修改。这样再创建唯一筛选索引，保证后续数据与业务规则一致。

后端覆盖：仅有效采购需求可创建、同明细只允许一条未关闭机会、创建下一步必填、候选基础条件、跨品类候选创建、重复候选拒绝、追加候选自动排除、中选前供应有效性、成功关闭中选校验、非成功关闭原因与中选互斥、采购需求完成/关闭/删除保护、未关闭机会下关键需求字段保护、候选当前状态派生、淘汰原因必填、关闭后不可编辑、关闭后新建下一轮、过程时间线完整性、权限拒绝和历史状态回填。

UI 测试在 `ui-tests` 中通过页面操作完成：在厂商详情创建和维护含多条明细的有效采购需求，并确认该区域没有任何撮合入口；在采购需求菜单确认撮合进度、进入采购明细选择弹窗、创建机会、追加候选、保留和淘汰候选、暂停恢复、关闭、重新撮合、刷新回查时间线和状态。测试还需验证同一 `demandId` 再次发起撮合时，缓存的撮合机会页仍会打开采购明细选择弹窗。测试使用隔离端口 `5174/5001`，不直接调用业务 API。
