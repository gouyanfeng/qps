# CRM 流转模块设计

**日期：** 2026-08-29  
**状态：** 已确认，待编写实施计划

## 1. 目标与范围

CRM 的药材基地主体和厂商都需要经历入库、分配、转交、退回待分配池。两者共享同一套流转语义和历史记录；药材基地明细只是主体的下属资料，不参与流转。

本次建立独立的 `CrmTransfers` 应用模块，统一负责人变更和流转历史，不引入额外的当前状态表或 `Service` 抽象。

### 包含

- 支持基地主体和厂商的入库、分配、转交、退回。
- 负责人变更与流转记录在同一次保存中完成。
- 详情页显示带流转类型的历史记录。
- 管理人员可分配、转交、批量操作；当前负责人可将本人负责的数据退回待分配池。
- 新建和导入均登记第一条入库记录。

### 不包含

- 药材基地明细的负责人和流转能力。
- 接收人确认、审批、撤回、时限催办。
- 额外的“待分配 / 我负责 / 已分配”列表筛选。
- 普通负责人直接转交给同事。第一期只允许其退回待分配池，再由管理人员分配或转交。

## 2. 核心模型

### 2.1 当前负责人

`CrmHerbBaseSubject.OwnerUserId` 与 `CrmVendor.OwnerUserId` 保留为当前负责人唯一事实来源：

- 非空：已分配给该用户。
- 空：位于待分配池。

不新增一对一的 `CrmTransfer` 当前状态表。该表会复制 `OwnerUserId`，每个列表查询都要额外关联，也不能表达独立业务事实。

### 2.2 流转历史

`CrmTransferRecord` 是不可变历史记录，使用已有的 `EntityType + EntityId` 关联业务对象。补充 `ActionType` 字段，采用下列固定代码：

| 代码 | 页面名称 | 起止负责人 | 说明 |
| --- | --- | --- | --- |
| `ENTRY` | 入库 | 空 -> 可空 | 对象首次进入 CRM；外部导入通常无负责人，人工新建通常由创建人负责。 |
| `ASSIGN` | 分配 | 空 -> 非空 | 从待分配池分配给负责人。 |
| `TRANSFER` | 转交 | 非空 -> 非空 | 在两名不同负责人之间变更。 |
| `RETURN` | 退回待分配池 | 非空 -> 空 | 移除负责人，重新进入待分配池。 |

`ActionType` 的存储代码由领域层常量 `CrmTransferActionType` 定义；流转对象类型由领域层常量 `CrmTransferEntityType` 定义，避免领域实体依赖应用层的 `CrmCodes`。页面只显示中文名称。现有索引 `(EntityType, EntityId, CreatedAt)` 保持不变，详情页按创建时间倒序查询即可。

### 2.3 领域职责

`CrmTransferRecord` 只负责保证一条记录自身合法，提供两个工厂方法：

- `CreateEntry(...)`：创建入库登记。允许目标负责人为空。
- `CreateOwnerChange(...)`：根据变更前后负责人自动判定 `ASSIGN`、`TRANSFER`、`RETURN`；前后负责人相同直接拒绝，避免无意义历史。

`CrmHerbBaseSubject` 与 `CrmVendor` 均提供 `ChangeOwner(...)`。该方法接收目标负责人、操作人和备注，先调用 `CrmTransferRecord.CreateOwnerChange(...)` 创建并校验流转记录，再更新自身 `OwnerUserId`，最后将记录返回。

实体不依赖 `DbContext`、不自行保存，也不持有流转记录集合。应用层取得返回记录后执行 `_dbContext.CrmTransferRecords.Add(record)`，并与聚合根在同一次 `SaveChangesAsync` 中提交。这样负责人变更和流转记录的业务规则在领域层，持久化边界仍在应用层。

## 3. 模块边界

```text
QPS.Domain
└─ Entities/Crm
   ├─ CrmTransferRecord.cs
   ├─ CrmTransferActionType.cs
   └─ CrmTransferEntityType.cs

QPS.Application
└─ Features/Crm/CrmTransfers
   ├─ ChangeCrmOwnerCommand.cs
   └─ CrmTransferRecords.cs
```

- `ChangeCrmOwnerCommand`：唯一的后续负责人变更用例，支持单条和批量对象。
- `CrmTransferRecords`：查询历史并批量补齐前负责人、后负责人、操作人的姓名。

创建与导入入口直接调用 `CrmTransferRecord.CreateEntry(...)`。当前仅有基地主体和厂商两处创建入口，没有必要再为这一行构造代码增加应用层辅助类。

原 `AssignCrmHerbBaseSubjectOwnerCommand`、`AssignCrmVendorOwnerCommand` 删除；对应控制器接口改为适配 `ChangeCrmOwnerCommand`。前端所有按钮、弹窗和提示统一使用“流转”术语。

厂商“编辑资料”请求不包含 `OwnerUserId`，`CrmVendor.Update(...)` 也不接收负责人。编辑资料只能修改厂商名称、优先级、采购摘要和备注；负责人只能在创建时确定初始值，或在后续通过流转变更，任何编辑入口不得绕过流转记录。

## 4. 用例与数据流

### 4.1 创建与导入

1. 外部导入创建主体或厂商时，`OwnerUserId` 为空。
2. 人工新建时，未显式指定负责人则将当前创建人作为负责人；有流转管理权限者可指定其他有效用户。
3. 对象加入 DbContext 后，直接调用 `CrmTransferRecord.CreateEntry(...)` 追加一条 `ENTRY` 记录。
4. 一次 `SaveChangesAsync` 同时写入业务对象和首条记录。

首条记录是生命周期登记，不调用 `CreateOwnerChange`。因此外部导入的“空 -> 空”合法，且不会被错误地当作退回操作。

### 4.2 后续流转

`ChangeCrmOwnerCommand` 请求仅包含对象类型、对象编号集合、目标负责人和备注；不接受流转类型，类型一律由当前负责人和目标负责人推导。

处理顺序：

1. 校验对象类型仅为 `CRM_HERB_BASE_SUBJECT` 或 `CRM_VENDOR`，并去重、校验对象编号。
2. 查询对应聚合，任何对象不存在即返回 404，避免部分成功。
3. 目标负责人非空时，校验其为有效用户。
4. 按权限规则校验本次操作。
5. 对每个对象调用聚合的 `ChangeOwner`，取得其创建的流转记录后加入 `CrmTransferRecords`。
6. 一次 `SaveChangesAsync` 提交所有对象和历史记录。

同一批量请求中，只要有一条无权限、目标无效或变更前后相同，整批失败并不写入数据。

### 4.3 查询与页面表现

详情查询由 `GetCrmTransferRecordsQuery` 按 `EntityType + EntityId` 获取记录，批量查询用户表后填充姓名。响应新增 `ActionType` 与 `ActionName`：

- 基地主体与厂商详情页均保留“流转记录”时间线。
- 每条显示“入库 / 分配 / 转交 / 退回待分配池”、前后负责人、操作人、备注、时间。
- 待分配对象显示“分配”；已分配对象显示“转交、退回”。
- 不新增归属筛选，也不改变详情页现有的其他维护入口。

## 5. 权限与操作边界

新增一个统一的管理权限码 `CRM_TRANSFER`，用于基地主体和厂商的分配、转交、批量流转。前端控制按钮可见性，后端命令必须再次校验，不能只依赖页面隐藏。

| 操作人 | 待分配 -> 某用户 | A -> B | A -> 待分配池 |
| --- | --- | --- | --- |
| 具备 `CRM_TRANSFER` 的管理人员 | 允许 | 允许 | 允许 |
| 当前负责人本人 | 不允许 | 不允许 | 仅允许退回本人负责的对象 |
| 其他普通用户 | 不允许 | 不允许 | 不允许 |

所有流转均直接生效，目标用户不需要确认。创建人默认负责人不是一条后续“分配”，仍只记录为 `ENTRY`。

## 6. 数据迁移与历史回填

迁移仅新增 `CrmTransferRecords.ActionType`，已有记录必须可无损升级：

1. 先以可空字段发布结构迁移。
2. 按历史记录的前后负责人回填：空到非空为 `ASSIGN`，非空到非空为 `TRANSFER`，非空到空为 `RETURN`。
3. 对无法推断的旧记录和所有现存对象的第一条历史统一回填 `ENTRY`；该步骤以每个 `EntityType + EntityId` 的最早记录为准。
4. 完成回填后改为非空，并设定默认值 `ENTRY` 以保护旧导入脚本。
5. 现有对象没有任何流转历史时，补一条 `ENTRY`：目标负责人取当前 `OwnerUserId`，操作人为空，备注写“历史数据初始化”。

回填在独立的迁移或一次性运维程序中执行，先在本地备份库验证记录数、对象覆盖数与类型分布，再用于正式库；不清空、不删除现有业务数据。

## 7. 错误处理

- 不支持的对象类型：400。
- 对象不存在、目标负责人不存在或已停用：404。
- 负责人未变化：400，提示“负责人未变化，无需流转”。
- 无 `CRM_TRANSFER` 且非本人退回：403。
- 批量请求任一对象不满足条件：整体失败，不产生部分流转记录。

## 8. 验收与测试

后端验证以下场景：

1. 外部导入主体、厂商均生成一条无负责人的 `ENTRY`。
2. 人工新建未指定负责人时，生成创建人为负责人的 `ENTRY`。
3. 管理人员分别执行分配、转交、退回，当前负责人和 `ActionType` 正确且同次保存。
4. 当前负责人仅能退回本人对象；无法分配或转交。
5. 相同负责人、无效用户、混入不存在对象的批量请求均不写入数据。
6. 主体和厂商详情的记录顺序、中文类型、人员名称正确。
7. 历史回填后，每个现存主体、厂商至少拥有一条流转记录，且负责人不被回填程序修改。

前端验证：待分配与已分配对象显示对应流转入口；分配、转交、退回后的列表负责人和详情时间线同步刷新。

## 9. 影响范围

- `CrmTransferRecord`、DTO、EF 映射与数据库迁移。
- 基地主体、厂商创建/导入、负责人变更命令和详情查询。
- 基地主体、厂商控制器及前端 API、流转弹窗和详情时间线。
- 权限种子数据与角色配置。

不修改跟进、评分、联系人、采购计划、基地明细的模型和流程。
