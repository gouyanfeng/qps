# 跟进任务工作台设计方案

## 1. 目标与范围

新增 CRM 一级菜单“跟进任务”，为销售人员提供基地主体和厂商的统一日常跟进入口。系统从现有业务对象的下次跟进时间派生任务，不新建任务表，不维护独立任务状态。

第一期只解决“当前登录人今天该跟谁、是否逾期、是否遗漏下次计划”。不建设团队看板、任务协作、提醒推送、任务分配、独立完成状态或撮合成交流程。

## 2. 业务对象与数据来源

| 对象 | 跟进摘要来源 | 是否进入工作台 | 排除条件 |
| --- | --- | --- | --- |
| 基地主体 | `CrmHerbBaseSubject.LastFollowAt`、`LastFollowResult`、`NextFollowAt` | 是 | 已删除 |
| 厂商 | 在 `CrmVendor` 新增同名三项字段 | 是 | 已删除 |
| 基地 | 现有字段仍保留 | 否 | 跟进业务已归属基地主体 |

`CrmFollowRecord` 仍是沟通明细的唯一来源。基地主体、厂商的三项摘要字段仅用于快速展示和待办筛选。

第一期基地主体、厂商统一只排除已删除数据；主体的成交、流失状态不参与工作台过滤。

## 3. 任务口径

以服务端北京时间的当天零点和次日零点为边界。

| 分类 | 规则 |
| --- | --- |
| 已逾期 | `NextFollowAt < 当前时间` |
| 今日待跟进 | `NextFollowAt >= 当天零点` 且 `< 次日零点` |
| 未来计划 | `NextFollowAt >= 次日零点` |
| 未设下次跟进 | `NextFollowAt == null` |
| 近 7 天已完成 | 最近 7 个自然日内成功新增的沟通记录数，不区分沟通结果 |

默认列表包含四类任务，排序固定为：已逾期、今日待跟进、未设下次跟进、未来计划；同类按下次跟进时间升序，无下次计划按最近跟进时间升序。

## 4. 页面设计

页面路径为 `/crm/follow-tasks`，菜单名为“跟进任务”。首页保留现有概览与提醒，不再新增明细区块。

页面由以下部分组成：

1. 顶部指标：已逾期、今日待跟进、未设下次跟进、近 7 天已完成。
2. 分类标签：全部、已逾期、今日、未来计划、未设计划。点击指标或标签切换当前列表分类。
3. 筛选区：对象类型、计划日期、名称/联系人/电话关键字。负责人固定为当前用户，第一期不提供跨人员筛选。
4. 分页列表：跟进对象、类型、联系人、上次跟进、下次跟进、最近结果、操作。
5. 行操作：`记录沟通` 为主操作，`详情` 为次操作。按对象类型打开主体或厂商详情。

“记录沟通”复用主体、厂商当前已有的沟通表单和提交接口。提交成功后刷新统计与当前列表，继续保留用户选择的分类和筛选条件。

## 5. 权限与数据范围

现有主体、厂商列表未实现可复用的数据范围体系。因此第一期工作台严格按 `OwnerUserId == 当前登录用户` 过滤，不能选择其他负责人，也不提供团队或全部数据视图。

菜单和“记录沟通”按钮沿用 CRM 现有权限模型。若厂商沟通目前未配置独立权限，统一使用现有 `CRM_HERB_BASE_FOLLOW`，避免第一期增加没有实际差异的权限点。

后续若需要管理者视图，应独立建设数据范围规则后再增加“负责人”筛选，不在本期通过角色名或管理员判断绕过数据范围。

## 6. 后端设计

### 6.1 厂商跟进摘要

`CrmVendor` 新增以下字段和领域方法：

- `LastFollowAt`
- `LastFollowResult`
- `NextFollowAt`
- `UpdateFollowSummary(DateTime followAt, string followResult, DateTime? nextFollowAt)`

领域方法只更新三项摘要字段。它不是任务状态机、事件或额外业务流程。

`CreateCrmVendorFollowRecordCommand` 在写入 `CrmFollowRecord` 后，对同一厂商调用 `UpdateFollowSummary`，再一次性保存。基地主体的 `CreateCrmFollowRecordCommand` 已使用同样模式，不调整其业务含义。

### 6.2 EF 数据库迁移和回填

使用 EF Core Migration 完成结构变更和一次性历史回填，不在 `TestDataInitializer` 中增加任何结构兼容、索引或数据修复逻辑。当前项目尚未建立 EF 迁移历史，先创建空的基线迁移并保留完整模型快照，使已有数据库只登记迁移版本而不重复建表；再创建本功能的增量迁移：

1. 为 `CrmVendors` 增加三项可空字段。
2. 创建 `(OwnerUserId, NextFollowAt)` 索引，优化本人待办的筛选和排序。
3. 在迁移的 `Up` 方法中，通过 SQL 按 `CrmFollowRecords` 中该厂商最新的一条未删除记录回填三项摘要：跟进时间使用记录的 `CreatedAt`，结果和下次跟进直接取记录字段。
4. 回填只处理三项摘要均为空的厂商，不覆盖已有摘要数据；`Down` 方法只回退本次新增结构，不尝试恢复历史摘要。

迁移部署使用 `dotnet ef database update` 或生成的幂等脚本执行，不改动当前 `TestDataInitializer` 的职责。开发环境仍可按现有方式通过 `EnsureCreated` 创建空库，再应用迁移版本记录和增量字段。

### 6.3 统一查询接口

新增应用层特性目录 `Features/Crm/FollowTasks`，只包含工作台查询及其 DTO：

- `GetCrmFollowTasksQuery`：分页、分类、对象类型、计划日期、关键字。
- `GetCrmFollowTasksHandler`：分别构造主体、厂商投影，使用 `Concat` 合并，再按统一待办排序分页。
- `CrmFollowTaskDto`：对象 ID、对象类型、名称、负责人、主联系人、上次跟进、下次跟进、最近结果、任务分类。
- `CrmFollowTaskOverviewDto`：四项顶部指标。
- `CrmFollowTaskResponse`：分页列表与概览指标的单一响应对象。

接口建议为 `GET /api/admin/crm/follow-tasks`。一个请求同时返回分页列表和概览指标，防止筛选操作产生多次请求；顶部指标始终按当前登录人的全部有效对象统计，不受列表分类与关键字影响。

关键字规则：主体匹配主体名称、主联系人、主联系电话；厂商匹配厂商名称、有效联系人及联系电话。

## 7. 前端设计

新增 `views/crm/followTask/index.vue` 与对应 API 模块、路由和菜单配置。

页面采用项目当前 Element Plus 表格、分页、筛选控件和权限组件，不引入新组件库。主体与厂商沟通弹窗暂不抽象成共享弹窗：两处既有页面逻辑可以通过路由打开详情并自动拉起“记录沟通”，工作台只负责跳转，避免本期复制或重构现有复杂表单。

工作台的“记录沟通”跳转规则：

- 基地主体：打开基地主体详情，带 `followId` 参数，由现有页面自动弹出沟通窗口。
- 厂商：打开厂商详情，带等价的 `followId` 参数；厂商页面补齐此参数处理以自动弹出既有沟通窗口。

详情返回工作台时不要求保留浏览器历史以外的页面状态；工作台重新进入时按默认分类重新请求。

## 8. 异常处理

- 未登录或当前用户 ID 无法解析：返回空列表与全零指标。
- 厂商无联系人：仍可进入工作台并记录沟通，沟通表单允许不选择联系人。
- 厂商沟通保存时联系人不属于当前厂商：沿用现有 404 业务异常。
- 已删除或不存在对象：跳转详情或保存沟通时沿用现有业务异常提示；工作台刷新后不再出现该行。

## 9. 验收标准

1. 当前用户只能看到自己负责的基地主体和厂商。
2. 基地主体、厂商均仅排除已删除数据；主体的成交、流失状态不影响是否出现在待办。
3. 四类任务的统计、标签数量和列表口径一致，时间边界以服务端北京时间为准。
4. 主体、厂商均可从任务列表进入详情并打开既有“记录沟通”窗口。
5. 成功保存主体或厂商沟通后，摘要字段、任务分类、列表和统计正确刷新。
6. 历史厂商存在沟通记录时，首次部署后能展示正确的上次、下次跟进摘要。
7. 首页、基地主体列表、厂商列表、已有沟通记录与详情页功能回归正常。

## 10. 非目标

- 不创建 `CrmTask` 或任务完成状态。
- 不增加消息提醒、定时催办、移动端适配。
- 不实现团队、部门、全部数据范围。
- 不改变基地与主体已经分离的维护入口。
