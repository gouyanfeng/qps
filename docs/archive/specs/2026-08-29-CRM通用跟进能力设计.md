# CRM 通用跟进能力设计

> **历史设计：** 通用跟进能力已实施，本文保留用于追溯设计决策。

**日期：** 2026-08-29
**状态：** 已实施，历史设计

## 1. 背景与目标

基地主体与厂商都是 CRM 跟进对象。两者已经共用 `CrmFollowRecord` 表，但应用层分别维护跟进记录的新增、查询逻辑，前端入口使用的权限码也不统一。

本次目标是将两类对象的跟进能力收敛为一个应用用例，并使用一个权限码控制跟进操作；不改变现有页面路由和 REST 地址。

## 2. 范围

### 包含

- 跟进记录新增和查询同时支持 `CRM_HERB_BASE_SUBJECT` 与 `CRM_VENDOR`。
- 两类对象继续使用 `CrmFollowRecord.EntityType`、`EntityId` 关联记录。
- 统一使用 `CRM_FOLLOW` 控制详情页和跟进任务工作台中的“记录沟通”操作。
- 基地主体保存跟进记录后继续触发评分重算事件。
- 厂商保存跟进记录后更新最近跟进摘要。

### 不包含

- 不新增跟进记录表、联系人表或新的领域服务。
- 不修改跟进记录的数据结构、接口路径和页面布局。
- 不合并基地主体、厂商和工作台的跟进弹窗组件；本次只统一业务用例与权限。
- 不调整“跟进任务”菜单权限 `CRM_FOLLOW_TASK`，该权限继续只控制菜单访问。

## 3. 领域模型

`CrmFollowRecord` 保持通用记录实体：

| 字段 | 说明 |
| --- | --- |
| `EntityType` | 跟进对象类型：`CRM_HERB_BASE_SUBJECT` 或 `CRM_VENDOR` |
| `EntityId` | 跟进对象标识 |
| `ContactId` | 可选联系人，必须属于该对象且未被软删除 |
| `FollowType`、`FollowResult`、`IntentLevel`、`Content`、`NextFollowAt` | 本次沟通内容与后续计划 |
| `OperatorUserId` | 当前操作人 |

聚合根继续拥有各自的摘要更新规则：

- `CrmHerbBaseSubject.UpdateFollowSummary`：更新最近跟进信息，并按结果推进主体状态。
- `CrmVendor.UpdateFollowSummary`：更新最近跟进信息。

不为两个实体引入仅含一个方法的接口或基类。应用层负责按对象类型编排，领域层负责更新自身状态。

## 4. 应用层设计

### 4.1 通用新增用例

`CreateCrmFollowRecordCommand` 接收对象类型、对象标识和记录请求。

处理顺序：

1. 校验沟通结果必填，且对象类型属于支持范围。
2. 按对象类型查询基地主体或厂商；对象不存在时返回 404。
3. 仅在指定联系人时校验联系人归属、对象类型和对象标识。
4. 创建一条 `CrmFollowRecord`，操作人取当前登录用户。
5. 调用对应聚合根的 `UpdateFollowSummary`。
6. 统一保存。
7. 对基地主体发布 `CrmHerbBaseSubjectScoreAffectedEvent`，厂商不发布事件。

厂商专用的 `CreateCrmVendorFollowRecordCommand` 删除，厂商控制器改为调用通用命令，并显式传入 `CRM_VENDOR`。

### 4.2 通用查询用例

`GetCrmFollowRecordsQuery` 同时支持两类对象：先按对象类型确认目标存在，再按 `EntityType + EntityId` 查询记录，关联联系人并按创建时间倒序返回。

厂商专用的 `GetCrmVendorFollowRecordsQuery` 删除，厂商控制器改为调用通用查询用例。

### 4.3 接口兼容

接口地址和请求、响应结构保持不变：

| 对象 | 查询 | 新增 |
| --- | --- | --- |
| 基地主体 | `GET /api/admin/crm/herb-base-subjects/{id}/follow-records` | `POST /api/admin/crm/herb-base-subjects/{id}/follow-records` |
| 厂商 | `GET /api/admin/crm/vendors/{id}/follow-records` | `POST /api/admin/crm/vendors/{id}/follow-records` |

控制器只负责固定对象类型后转发到通用查询或命令，前端 API 模块无需调整。

## 5. 权限设计

新增统一操作权限 `CRM_FOLLOW`，名称为“记录跟进”。

| 位置 | 调整 |
| --- | --- |
| 基地主体列表及详情 | 原 `CRM_HERB_BASE_FOLLOW` 改为 `CRM_FOLLOW` |
| 厂商详情 | 原 `CRM_VENDOR_EDIT` 改为 `CRM_FOLLOW` |
| 跟进任务工作台 | “记录沟通”按钮增加 `CRM_FOLLOW` 校验 |
| 跟进任务菜单 | 保持 `CRM_FOLLOW_TASK` |

数据库迁移需幂等创建 `CRM_FOLLOW`，挂在 CRM 权限树下，并授予系统管理员角色。旧的 `CRM_HERB_BASE_FOLLOW` 仅在确认无其他使用处后移除。

## 6. 数据与事务

跟进记录和聚合摘要在同一次 `SaveChangesAsync` 中保存。基地主体评分事件在保存成功后发布，沿用现有事件机制，确保评分计算读取到已落库的跟进摘要与记录。

本次不做历史数据迁移：现有厂商和基地主体记录的 `EntityType` 已可被通用查询识别。

## 7. 验收与测试

后端自动化验证：

- 厂商通过通用命令新增记录，记录类型、联系人、操作人和厂商跟进摘要正确。
- 基地主体通过通用命令新增记录，主体摘要正确且评分事件被发布。
- 两种对象的跨对象联系人均被拒绝。
- 两种对象均可按对象类型查询到自身记录，且对象不存在时返回 404。

前端验证：

- 具备 `CRM_FOLLOW` 的用户可在基地主体详情、厂商详情和跟进任务工作台打开并保存沟通记录。
- 不具备 `CRM_FOLLOW` 的用户不显示“记录沟通”入口。
- 厂商、基地主体的原有详情跳转与记录时间线正常。

工程验证：

- 后端构建和单元测试通过。
- 前端构建通过。
- 数据库迁移可在已有数据库上执行，重复执行不重复创建权限。
